Chapter 7

Domain modules — a reusable picker over store-scoped data

Chapter 6 gave us a store-scoped cache: locations, master lists and reasons, fetched once per store and shared. But a cache isn't a picker. Every screen that let you choose a location was re-wiring the same <Combobox> — same resource read, same itemToString, same loading — and the wiring had already drifted. A src/domain/<entity>/ module is the fix: one home for the data and its picker.

Three layers, not two

Until now the app had two layers: src/api (transport) and src/ui (a pure, data-agnostic component library). A picker over locations fits neither, and that mismatch is the whole reason this chapter exists.

  • Not src/api. That's the transport layer — graphqlFetch, the codegen output, the resource primitive. A rendered <Combobox> doesn't belong there; it would make api ship UI.
  • Not src/ui. The component library imports nothing from the app (that's what keeps it showcase-isolable). An <EntitySelect> imports a resource from api and encodes domain knowledge (which reason types apply) — putting it in ui breaks that boundary.

So we add a third layer, src/domain/, for widgets that know both the app's data and how to render it.

The dependency order (memorise this)

domain sits between api and ui: it may import both — api for the resource, ui for the Combobox. But ui imports neither api nor domain, and api imports nothing above it. Verticals under sections/ compose domain selects + ui components. If you ever find ui reaching into domain, the layering has inverted.

Anatomy of a domain module: four files

A folder-per-entity co-locates everything about one reference entity. Here is src/domain/location/ in full — four files (plus the codegen output):

  • location.graphql — the operation. Codegen walks src/**/*.graphql and drops a co-located location.generated.ts next to it, so the query lives beside everything that uses it.
  • locationResource.ts — the state binding: a createStoreScopedResource from chapter 6, plus the exported node type.
  • LocationSelect.tsx — the picker: a thin, self-fetching wrapper over the ui/ Combobox.
  • index.ts — re-exports the resource + type (for non-select reads, e.g. a .find() lookup) and the select. The module's public surface.
src/domain/location/locationResource.ts 
// One location node (id + code + name) — derived from the generated result,
// never restated (kdd/type-safety).
export type Location = LocationsResult['locations']['nodes'][number];

// App-wide locations cache: store-scoped, lazy, deduped, read via .noSuspense().
export const locationsResource = createStoreScopedResource<Location>(
  currentStoreId,
  async storeId => {
    const result = await graphqlFetch(Locations, { storeId });
    return result.kind === 'success' ? result.data.locations.nodes : undefined;
  }
);

The resource is exactly the chapter-6 pattern — the new part is that it lives inside the entity's folder, not under src/api, so the query, the cache and the picker are one unit.

The self-fetching thin select

Here is the pay-off. The caller passes only value + onChange (+ an a11y label). The select owns everything data-shaped: the .noSuspense() resource read, itemToString/itemToValue, and loading. Nothing about the locations cache leaks to the call site.

src/domain/location/LocationSelect.tsx 
export interface LocationSelectProps {
  value?: string;                                // selected location id
  onChange: (location: Location | null) => void;   // hands back the FULL node
  label: string;                                // required for a11y
}

export const LocationSelect = (props: LocationSelectProps): JSX.Element => (
  <Combobox<Location>
    label={props.label}
    items={locationsResource.noSuspense()}   // never suspends the screen it's on
    loading={locationsResource.loading()}
    itemToString={l => l.code}                // ONE label format, app-wide
    itemToValue={l => l.id}
    value={props.value}
    onChange={l => props.onChange(l)}          // full node → caller can store code/name
  />
);

Why hand back the full node?

onChange reports the whole Location (id + code + name), not just the id, because callers persist that alongside the id — the stocktake line stores a location object, so it can render the code without a second lookup. Id-only callers just read .id. This is the no-remapping rule: the select reports the domain shape the caller already stores, so nothing gets flattened to a parallel type. (MasterListSelect, whose caller only needs the id, reports id-only — onChange={m => props.onChange(m?.id ?? null)}.)

Variants are props, not new components

The reasons list is global and spans many types; each screen wants a slice. The tempting move is a PositiveReasonSelect and a NegativeReasonSelect — but then the filter set is re-declared per component. Instead the variant is a kind prop, and the filtering lives in one place.

src/domain/reasonOptions/ReasonSelect.tsx 
export type ReasonKind = 'adjustment' | 'reduction';

// The one source of truth for which reason types each use case offers.
const KIND_TYPES: Record<ReasonKind, ReadonlySet<ReasonOption['type']>> = {
  adjustment: new Set(['POSITIVE_INVENTORY_ADJUSTMENT', 'NEGATIVE_INVENTORY_ADJUSTMENT']),
  reduction:  new Set(['NEGATIVE_INVENTORY_ADJUSTMENT']),
};

// Exported so non-select needs (resolving a label) filter the same way.
export const reasonsOfKind = (kind: ReasonKind): ReasonOption[] =>
  reasonOptionsResource.noSuspense().filter(r => KIND_TYPES[kind].has(r.type));

<ReasonSelect kind="adjustment" … />   // stocktake line editor (both directions)
<ReasonSelect kind="reduction" … />    // reduce-to-zero (negative only)

Now the type-filter set is enumerated once, reasonsOfKind is reusable outside the select, and every caller offers exactly the reasons its use case allows — by naming a kind, not by re-deriving a filter. That's the explicit-composition reflex: name and enumerate the variants in one file.

The current domain modules

Run ls src/domain/ and you get exactly four folders:

  • location — the canonical example above.
  • masterList — same shape, reports id-only.
  • reasonOptions — the kind-prop variant.
  • debouncedEdit — not an entity module. domain/ also hosts non-entity domain helpers that bridge app data + behaviour but aren't reference lookups: createDebouncedEdit is the buffered, per-field save-as-you-type edit store the stocktake side panel uses (chapter 8's cousin). Those get a concern-named folder rather than an <entity>/ one.

Rule of three, not reflex

A picker used in a single vertical can just live in that sections/ folder. domain/ is for the reused ones — each of these had two-to-three call sites and drifting duplication (the location label was l.code in two places and `${l.code} — ${l.name}` in a third). Promote to domain/ when reuse is real, not on the first use.

Build step · widgets

Add a src/widgets/widgetCategory/ domain module — four files, matching location/ exactly: widgetCategory.graphql (a widgetCategories(storeId) query), then run pnpm codegen to emit the co-located .generated.ts; widgetCategoryResource.ts wrapping createStoreScopedResource(currentStoreId, …) plus an exported WidgetCategory type; WidgetCategorySelect.tsx, a thin <Combobox> that reads .noSuspense()/.loading() and takes only value + onChange + label; and an index.ts re-exporting all three. Now drop <WidgetCategorySelect> into your widgets create form — the call site never touches the resource. Bonus: give it a kind prop like ReasonSelect if categories come in flavours.
