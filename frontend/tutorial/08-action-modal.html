Chapter 8

Action modals — a confirm → working → success | error phase machine

A destructive or bulk action isn't a fire-and-forget click. It's a small story: ask, work (with visible feedback and no way to double-submit), then confirm success or show the failure in context. Each such action here is a self-contained component that owns one <Dialog> driven through four phases — confirm → working → success | error — and hands its result back to the view to apply in place, no refetch.

Why one dialog owns the whole lifecycle

The alternative — a modal that emits onConfirm(value) and closes immediately, with the view running the mutation fire-and-forget and a separate error dialog surfacing failures afterwards — was the shape these actions started in. It gave no in-flight feedback, no success confirmation, and split one logical action across two dialogs. The decision was to fold it all into one:

  • In-flight feedback + success confirmation is the expected UX for a bulk/destructive action; splitting confirm and error across two dialogs reads as unfinished.
  • Blocking while working — the dialog goes non-dismissable (no scrim / Escape exit) and the confirm button goes loading — prevents a double-submit or an ambiguous half-closed state.

There is no shared ActionModal

An earlier draft of the KDD describes a shared SelectionActionModal in src/domain/selection/. That was superseded — a later commit inlined the phase machine into each action, and there is no src/domain/selection or src/domain/action in the tree today. The phase machine is repeated (a few lines) in each action rather than abstracted, on purpose: the whole flow — mutation, transitions, what each phase renders — reads in one place (explicit composition). Don't reach for a shared import that doesn't exist.

The four phases

Every action names its phase the same way and mounts the machine only while the dialog is open:

src/sections/stocktakes/detail/actions/DeleteLinesAction.tsx 
type Phase = 'confirm' | 'working' | 'success' | 'error';

export const DeleteLinesAction: Component<DeleteLinesActionProps> = props => {
  const [open, setOpen] = createSignal(false);
  return (
    <>
      <Button icon={<TrashIcon />} disabled={props.disabled} onClick={() => setOpen(true)}>
        {t('common.delete')}
      </Button>
      {/* Body mounts only while open → the phase is FRESH per open. */}
      <Show when={open()}>
        <Body {...props} onClose={() => setOpen(false)} />
      </Show>
    </>
  );
};

Why the phase lives in a mounted-while-open child

The button is the always-mounted outer component; the phase (createSignal<Phase>('confirm')) and any inputs live in an inner <Body> that only exists while open(). So the machine is fresh on every open — no manual reset — and a late-resolving run() from a prior open lands on a disposed scope rather than mutating a reused signal. The selected count is snapshotted once on open, so the confirm/success message can't shift if the selection changes behind the dialog.

run() → a discriminated result; who owns what

The split of ownership is the crux: the modal owns the phase and its presentation; the view owns the data mutation, applied in place. run() calls the mutation layer, which returns a discriminated outcome, and drives the phase from it — while handing the successful part back to the view via callbacks.

…/actions/DeleteLinesAction.tsx — the Body's run() 
const run = async () => {
  if (phase() !== 'confirm') return;        // re-entry guard
  setPhase('working');                        // button → loading, dialog → non-dismissable

  const outcome = await runBatchStocktakeLines(props.storeId, {
    delete: props.selectedIds().map(id => ({ id })),
  });

  // undefined = transport / NodeError → the GLOBAL modal already showed it.
  // Nothing per-line to reflect; just close (never stuck in 'working').
  if (!outcome) return props.onClose();

  props.onCommit(outcome.commit);              // VIEW splices what saved (no refetch)
  if (outcome.errors.size === 0) return setPhase('success');

  props.onError(outcome.errors);              // stamp per-line errors so the rows show them
  setErrorCount(outcome.errors.size);
  setPhase('error');                          // → Cancel + "Show error lines"
};

The mutation layer is where the discriminated result is minted. For the line actions it is runBatchStocktakeLines, which returns BatchStocktakeLinesOutcome | undefined:

src/sections/stocktakes/detail/lines/stocktakeLineUpdate.ts 
export type BatchStocktakeLinesOutcome = {
  commit: LineEditCommit;   // inserted / updated nodes + deletedIds — apply in place
  errors: LineErrors;      // Map<lineId, error __typename> — partial failure is normal
};

// undefined ⇒ the whole call failed at transport / NodeError level (already
// surfaced by the global modal), so there is nothing per-line to reflect.
const outcome: BatchStocktakeLinesOutcome | undefined = await runBatchStocktakeLines(…);

The modal owns phase; the caller owns the data

run() never mutates rows itself. It calls props.onCommit(commit) / props.onError(errors) and the view applies them — the same success-reflected-in-place, no-refetch model as everywhere else. This is chapter 5's idea: the view's createResource is written back with mutate(), so the screen updates without remounting. Note the actions don't clear the selection on success: they host their modal inside the selection footer, so clearing would unmount the modal mid-success-phase. Selection clears when the modal closes, by which point the success/error phase has been seen.

The view side — mutate() applies the commit in place

The detail view wires each action's callbacks to a single applyCommit that reduces every path (full line-edit commit, or a delete-only / update-only partial from an action) to one splice via the resource's mutate:

src/sections/stocktakes/detail/StocktakeDetailView.tsx 
const applyCommit = (commit: Partial<LineEditCommit>) => {
  mutate((node) => {                          // no refetch — patch the resource in place
    if (!node) return node;
    const deleted = new Set(commit.deletedIds);
    const updatedById = new Map((commit.updated ?? []).map(l => [l.id, l]));
    const nodes = node.lines.nodes
      .filter(l => !deleted.has(l.id))
      .map(l => updatedById.get(l.id) ?? l)
      .concat(commit.inserted ?? []);
    return { ...node, lines: { ...node.lines, nodes } };
  });
  // … also clears any stale per-line error on ids that just committed.
};

// wired straight into each action:
<DeleteLinesAction
  selectedIds={selectedIds} disabled={locked()}
  onCommit={applyCommit} onError={stampErrors} onShowErrors={showErrors} />

Global transport errors vs local domain errors

This is the standing split (chapter 2's global error modal). Only one of the two kinds of failure becomes the error phase:

Failure Where it surfaces What the modal does
Transport / unexpected — the request itself failed (network, a NodeError) The global reload-me modal, already, via graphqlFetch outcome is undefined → the modal just closes; it never sits stuck in working
Domain — the server rejected specific lines (a per-line batch error, a validation rejection) Locally, in this action's own lifecycle Becomes the error phase, in context, with the mapped message

"the reload-me modal for the request itself failed; an in-context phase for the server rejected these lines." The if (!outcome) return props.onClose() line in every action is the transport branch.

The error phase's "Show error lines"

When domain errors carry line ids, the error phase does more than report — it routes forward. It shows the server-mapped summary and offers Cancel + Show error lines, which calls onShowErrors() (the view wipes every other filter and keeps only the stamped error rows) and closes. This folds what used to be a separate error dialog into the action's own lifecycle.

…/actions/DeleteLinesAction.tsx — the error-phase actions 
<Match when={phase() === 'error'}>
  <Button variant="secondary" icon={<XCircleIcon />} onClick={props.onClose}>
    {t('common.cancel')}
  </Button>
  <Button variant="primary" icon={<SearchIcon />}
    onClick={() => { props.onShowErrors(); props.onClose(); }}>
    {t('stocktake.errors.show')}
  </Match>

The whole dialog is one <Dialog> whose description and actions are each a <Switch> on phase(): dismissable={phase() !== 'working'} is the entire blocking rule; loading={phase() === 'working'} on the confirm button is the entire in-flight feedback; <Show when={phase() === 'confirm'}> around Cancel hides it while working.

Finalise is an action too

FinaliseAction runs the same four-phase machine, with two differences that make it a good second example rather than a copy:

  • Its trigger is the status stepper's SplitButton in the footer, not a plain selection button — so it's a footer action, not a selection action, but the confirm → working → success | error dialog is identical in shape.
  • It carries a second, "nothing counted yet" guard dialog: pressing finalise with no countable lines opens an info-only dialog (single OK) explaining why it can't run, rather than a silent no-op or a dead confirm.
src/sections/stocktakes/detail/actions/FinaliseAction.tsx 
const openConfirm = (status: string) => {
  if (props.disabled) return;               // locked/finalised — split button hidden anyway
  if (!props.canFinalise) return setNoLinesOpen(true);   // the "nothing counted" guard dialog
  setPhase('confirm');
  setPendingStatus(status);                // != null opens the finalise confirm dialog
};

const run = async () => {
  if (phase() !== 'confirm') return;
  setPhase('working');
  const result = await finaliseStocktake(props.storeId, props.node.id);
  if (result.kind === 'failed') return close();        // transport → global modal; just close
  if (result.kind === 'saved') {
    props.onApplied(result.node);                    // view merges the FINALISED node in place
    return setPhase('success');
  }
  props.onError(result.lineIds);                     // SnapshotCountCurrentCountMismatch → stamp rows
  setPhase('error');
};

Its result type StocktakeFinaliseResult is a three-way discriminant — { kind: 'saved'; node } | { kind: 'error'; message; lineIds } | { kind: 'failed' } — the same three destinations (success / local error / global-and-close) spelled as one union rather than "outcome-or-undefined". Same three branches, different shape at the seam.

Build step · widgets

Give the fictional widgets/ vertical a bulk "archive selected" action with the same confirm → working → success | error shape. Model it on DeleteLinesAction: an ArchiveWidgetsAction component owning its button + a <Show when={open()}> inner <Body> that holds createSignal<Phase>('confirm'). Its run() calls a runArchiveWidgets(storeId, ids) layer that returns { commit, errors } | undefined; undefined → close (transport handled globally), errors.size === 0 → onCommit + success, otherwise onError + the error phase with a "Show error widgets" button (onShowErrors). Keep the dialog dismissable={phase() !== 'working'} and the confirm button loading={phase() === 'working'}. The widgets list view applies the commit with its resource's mutate() — no refetch.

Recap

  • Each action is a self-contained component: its own button, its own phase state, and its own inlined <Dialog> — no shared modal import.
  • Four phases in one dialog: confirm → working → success | error. Working blocks (non-dismissable + loading button) so there's no double-submit.
  • run() reads a discriminated result from the mutation layer, owns the phase, and hands the successful part to the view via callbacks; the view applies it in place with mutate() — no refetch (chapter 5).
  • Transport failures stay global (the modal just closes); only domain failures become the error phase, which can route forward to "Show error lines".
  • Finalise uses the same machine as a footer action, plus a "nothing counted yet" guard dialog.
