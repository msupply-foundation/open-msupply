Chapter 2

Init, auth & the global error component

How the app boots, how a user logs in, and how errors surface. The theme of this chapter: global state is module-level signals — there is no provider tree and no createContext. Files named authContext.ts are modules, not React contexts.

The entry point

src/index.tsx renders <App/> into #root. That's nearly all it does — the only branch is a dev-only showcase that is dead-code eliminated from production.

src/index.tsx 
import { render } from "solid-js/web";
import { App } from "./App";

const root = document.getElementById("root")!;
render(() => <App />, root);

A phase machine, not a router-first app

App.tsx is a small state machine with three phases. Routing is only mounted once the app is operational and a user is present. Startup runs in a fixed order and never navigates away from the original URL, so a deep link is respected once auth resolves.

src/App.tsx (abridged) 
type Phase = "loading" | "initialisation" | "operational";
const [phase, setPhase] = createSignal<Phase>("loading");

const runStartup = async () => {
  await initialiseLocale(detectLocale());          // 1. dictionary before first paint
  const status = await graphqlFetch(InitialisationStatus, {});
  if (status.kind !== "success") return;         // failure handled globally; stay loading
  if (status.data.initialisationStatus.status !== "INITIALISED") {
    setPhase("initialisation"); return;
  }
  if (await checkAuth()) setPhase("operational");  // 2. me check
};

onMount(() => { void runStartup(); … });

And the render: routing appears only when operational and a user exists. 

<Match when={phase() === "operational"}>
  <Show when={authUser()} fallback={<LoginPage />}>
    <Router> … </Router>
    <ReLoginModal />
  </Show>
</Match>
/* On top of EVERYTHING, including modals: */
<UnexpectedErrorModal />

No provider tree

Notice there are no context providers wrapping the app. authUser() is a signal imported straight from a module. Reactivity — not dependency injection — wires the app together. This is the single most surprising thing for developers arriving from React.

Auth is a module of signals + actions

All authentication lives in src/auth/authContext.ts: the user signal, the session flags, and the actions that change them. The user is typed to the generated fragment — no parallel model (chapter 1's type-safety rule).

src/auth/authContext.ts (abridged) 
// State from GraphQL keeps its generated type — the same fragment backs me AND login.
export type AuthUser = UserInfoFragment;

const [user, setUser] = createSignal<AuthUser | undefined>();
export const authUser = user;                      // the global read accessor

export const checkAuth = async () => {          // startup me check
  const result = await graphqlFetch(Me, {});
  if (result.kind === "success") { setUser(result.data.me); return true; }
  return result.kind === "unauthenticated";
};

export const login = async (username, password) => {
  const result = await graphqlFetch(AuthToken, { username, password });
  if (result.kind !== "success") return { kind: "pending" }; // global failure
  const auth = result.data.authToken;
  if (auth.__typename === "AuthTokenError") return { kind: "error", message: auth.error.description };
  setUser(auth.user); clearUnauthenticated(); return { kind: "success" };
};

The login page is a thin consumer: local signals for the fields, and on success it just calls login(). There is no success callback — setting the global user signal is what makes App swap the login page for the router.

Sessions are cookie-based

Nothing auth-sensitive is stored client-side — no token in localStorage, no Authorization header. The server sets an HttpOnly session cookie and graphqlFetch sends credentials: "same-origin". The user identity lives only in the in-memory signal. (startActivityTracking() fires a RefreshToken when the user is active but GraphQL traffic has been idle, and flips an inactivity flag otherwise.)

The global error component

Recall from chapter 1 that any unhandled failure sets a global signal inside graphqlFetch. Here is the whole surfacing mechanism — a signal in the API layer, and one modal that reads it.

src/api/graphql.ts 
// One global failure state for anything outside the structured union results.
const [unexpectedError, setUnexpectedError] = createSignal<string | undefined>();
export { unexpectedError };
// …inside graphqlFetch, on any unhandled failure:
setUnexpectedError(message);
return { kind: "unexpectedError" };
src/UnexpectedErrorModal.tsx 
export const UnexpectedErrorModal = () => (
  <Dialog
    open={Boolean(unexpectedError())}
    dismissable={false}                         // recovery IS the only exit
    title={t("error.unexpected")}
    description={unexpectedError()}
    actions={<>
      <Button onClick={() => location.reload()}>{t("error.reload")}</Button>
      <Button onClick={() => (location.href = "/")}>{t("error.go-to-dashboard")}</Button>
    </>}
  />
);

Errors are values, handled once

There is no ErrorBoundary and no thrown-exception path. A failure is a value that trips a signal; a single modal renders it, and the flow that hit the error simply stays in its loading phase. Its sibling, ReLoginModal, handles the unauthenticated case differently — it preserves the user's workflow (doesn't clear the user) rather than reloading.

Build step · widgets

Your widgets route will live inside the router, which only mounts when authUser() is set — so it inherits auth-gating for free, no guard code. To see the error path: make a widgets fetch hit a bad endpoint and watch the UnexpectedErrorModal appear over the whole app while your list stays in its loading state.
