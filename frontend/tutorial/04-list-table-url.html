Chapter 4

The list screen: URL state, table, variables

The reference list screen is StocktakesList.tsx. Its filter, sort, and pagination live in one JSON URL parameter; a DataTable renders the rows but owns none of that state; and a single memo turns URL state into typed GraphQL variables. Every type is a generated GraphQL type — no parallel models.

The whole loop, at a glance

?query= URL
→
useUrlQueryState
→
variables memo
→
graphqlFetch
→
rows → DataTable

A header click / filter edit / page change writes back into the URL, which flows around the loop again. The URL is the single source of truth for list state — so a list is shareable and back-button-correct.

URL as state, in one JSON param

Rather than spread ?sort=name&dir=asc&page=2&filter.status=… across many named params, all list state is one JSON blob under ?query=. useUrlQueryState<T> is generic over that shape; each list supplies its own T and a default.

src/list/urlQueryState.ts 
export function useUrlQueryState<T extends object>(defaultState: T) {
  const [searchParams, setSearchParams] = useSearchParams<{ query: string }>();

  const state = (): T => {
    const raw = searchParams.query;
    if (!raw) return defaultState;
    try { return { ...defaultState, ...(JSON.parse(raw) as Partial<T>) }; } // merge over default
    catch { return defaultState; }
  };

  const setState = (next: T, options?) => {
    const serialised = JSON.stringify(next);
    // A state equal to the default → drop the param, so a pristine list has a clean URL.
    const query = serialised === JSON.stringify(defaultState) ? null : serialised;
    setSearchParams({ query }, { replace: !options?.push });
  };
  return { state, setState };
}

Two deliberate choices

  • Merge over the default so a partial or older URL still yields full state.
  • No validation against T. A hand-edited bad URL flows through to a GraphQL error, surfaced by the global modal — the right outcome for a malformed link, and far less machinery than guarding every field.

The list's state type is the generated GraphQL shapes — no remapping:

src/sections/stocktakes/StocktakesList.tsx 
type StocktakesListState = {
  filter: StocktakeFilter;                     // = NonNullable<Variables["filter"]>
  sort?: StocktakesVariables["sort"];         // the generated sort input array
  offset: number;
  first: number;
};
const { state, setState } = useUrlQueryState<StocktakesListState>(DEFAULT_STATE);

From URL state to GraphQL variables

One memo assembles the store (from the path) and the URL state into the generated Variables shape. stripEmpty drops "added but empty" filter chips so they don't perturb the query. 

const variables = createMemo<StocktakesVariables>(() => ({
  storeId: params.storeId,
  filter: stripEmpty(state().filter),
  sort: state().sort,
  page: { first: state().first, offset: state().offset },
}));

The three interactions all funnel back through setState: 

const onSort = (key, desc) => setState({ ...state(), sort: [{ key, desc }], offset: 0 });
const onFilterChange = (filter) => setState({ ...state(), filter, offset: 0 });
// pagination: onOffsetChange / onPageSizeChange → setState({ …, offset / first })
// note: sort and filter both RESET offset to 0.

Filters are exhaustive and type-driven

The filter definitions are a Record keyed by every field of the generated filter input — each field maps to a control (expose it) or null (dismiss it). If the schema gains a filter, codegen adds the key and this map stops compiling until you decide expose-or-dismiss. Nothing is exposed by accident.

src/sections/stocktakes/listFilters.tsx (shape) 
const FILTERS = constructFilters<StocktakeFilter>({
  status:      { label: () => t("…"), render: … },   // exposed, in display order
  description: { label: () => t("…"), render: … },
  // … dismissed (not user-facing): the type forces every key to appear …
  stocktakeDate: null,
  id: null, userId: null, programId: null,
});

The DataTable owns display, not state

DataTable is headless TanStack Table under a hand-rolled semantic <table>. It routes as much state logic through TanStack as TanStack genuinely owns (the sort-toggle cycle, select-all/indeterminate bookkeeping, column accounting) — but the state itself is controlled and page-owned. The table mirrors your props in and calls back out; it never persists anything.

Why (KDD)

A table is the one sanctioned config-driven exception (N columns × M rows is genuinely tabular). "Buy the hard" — TanStack does the gnarly interaction logic; we own markup, CSS, and all the persisted state. See kdd/table-state.

Columns are an accessorKey-first extension of TanStack's ColumnDef:

src/ui/elements/table/DataTable.tsx 
// The ONE typed extension: sortKey — the GraphQL sort field, typed to a real union K.
export type Column<T, K extends string> = ColumnDef<T> & { sortKey?: K };
export type SortState<K extends string> = { key: K; desc: boolean };

The extension rule

A display-only flag (text alignment, wrap-lines, card region) goes in TanStack's meta bag — augmented once, typed everywhere. A convention that must carry a table-specific type (the sort-key union K) becomes a real field on Column<T,K> — because module augmentation of ColumnMeta can't carry K (it would degrade to string and break end-to-end typing).

Column values are derived from the generated result type — the row is a node: 

type StocktakeRow = StocktakesResult["stocktakes"]["nodes"][number];
// Sortable columns can only name a REAL sort key — the generated union:
type SortKey = NonNullable<StocktakesVariables["sort"]>[number]["key"];

const columns = (): Column<StocktakeRow, SortKey>[] => [
  { accessorKey: "stocktakeNumber", sortKey: "stocktakeNumber", header: "#", ...getNumberCell() },
  { accessorKey: "status", sortKey: "status", header: t("…"),
    cell: (info) => <StatusChip {...statusMeta(info.getValue())} /> },
  // …
];

(Columns are an accessor () => [...], not a plain array, so the t()-driven headers re-translate on a language switch — read reactively when passed as a prop.)

The table is wired controlled — state in via props, changes out via callbacks: 

<DataTable
  columns={columns()}
  rows={rows()}
  rowKey={(r) => r.id}
  sort={currentSort()}          onSort={onSort}          // URL owns sort
  selectedIds={selectedIds()}   onSelectionChange={setSelectedIds}  // page signal
  onRowClick={openRow}
/>

Pagination stays out of the table

DataTable has no pagination row model. The Pagination component is pure presentation over the page-owned offset/first/total — the arithmetic is trivial and the state is the URL's. The KDD explicitly rejects wiring TanStack's pagination model in.

Build step · widgets

Build WidgetsList: define WidgetsListState from the generated types, call useUrlQueryState, write the variables memo, and render a DataTable with columns typed Column<WidgetRow, WidgetSortKey>. Wire onSort, filters, and Pagination back through setState. You now have a shareable, URL-driven list — except it can't fetch yet. That's chapter 5.
