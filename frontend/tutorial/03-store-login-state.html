Chapter 3

Store login & the global-state shape

A user has many stores; working in the app means entering one. This chapter introduces the canonical signal-plus-refetch pattern for GraphQL-backed global state — the shape you'll reuse everywhere — and the principle that ties the whole state model together: refresh by direct call, not cache keys.

User auth ≠ store entry

Chapter 2 got a user. But the same user may belong to several stores, each with its own preferences and permissions. The URL encodes which store you're in: /{storeId}/{route}. Entering a store loads its context.

Why (KDD)

The store id is the first URL segment (/{store-uuid}/{route}?query=…). Filter/sort/pagination ride in that ?query= JSON (chapter 4). See kdd/url-structure.

The canonical global-state shape: signal + explicit refetch

Store context is the template every piece of GraphQL-backed global state follows: a plain signal, and an explicit async refetch function whose fetcher runs a codegen document through graphqlFetch. On failure it leaves the state empty (the failure was handled globally in chapter 1), so callers simply keep showing their loading state.

src/store/storeContext.ts 
const [storeContext, setStoreContext] = createSignal<StoreContextResult>();

const refetch = async (storeId: string | undefined) => {
  if (!storeId) { setStoreContext(undefined); return; }
  const result = await graphqlFetch(StoreContext, { storeId });
  if (result.kind !== "success") { setStoreContext(undefined); return; }
  setStoreContext(result.data);
};

export { storeContext, refetch as refetchStoreContext };

Two derived accessors read out of that signal. They are exported at module level — deliberately, so that global caches can depend on them without being inside a component (you'll use exactly this in chapter 6). 

// The store the user has ENTERED (context loaded). undefined between store switches.
const currentStoreId = () => storeContext()?.storePreferences.id;
const currentUserId  = () => storeContext()?.me?.userId;
export { currentStoreId, currentUserId };

Why module-level accessors matter

currentStoreId() is reactive but not tied to any component's lifecycle. A module-scope cache can read it and re-fetch when it changes. It's only non-undefined once the guard (below) has resolved and authorised the store from the URL — so it's URL-driven in effect, and never reports a store whose lookups aren't yet valid to fetch.

The store guard

StoreGuardLayout is the outermost routed layer — the /:storeId route. It decides which store to enter, loads its context, and shows a loading state until that context is loaded for this store and this user. Only then does it render the routed section.

src/store/StoreGuardLayout.tsx (the core) 
const storeToEnter = () =>
  stores().find((s) => s.id === params.storeId) ??
  (stores().length === 1 ? stores()[0] : undefined);   // sole store auto-enters

// Loaded ONLY when both store id AND user id match — so re-login as a different
// user reloads context even for the same store.
const contextLoaded = (storeId) => {
  const context = storeContext();
  return context?.storePreferences.id === storeId && context.me.userId === user()?.userId;
};

createEffect(() => {
  const store = storeToEnter();
  if (!store) return;                                    // → renders the store picker
  if (params.storeId !== store.id) navigate(`/${store.id}`, { replace: true });
  if (!contextLoaded(store.id)) void refetchStoreContext(store.id);  // direct call
});

The render is two nested <Show>s: no store to enter → the picker; store chosen but context not yet loaded → a loading screen; otherwise the section (props.children). This is why a list screen in chapter 4 can assume storeId is always present and its context is loaded.

Refresh by direct call, not cache keys

This is the through-line of the entire state model. There is no cache-invalidation system. When something needs to refresh, whatever observed the need calls the specific refetch function. Logout is the clearest example — it directly clears the store context:

src/auth/authContext.ts 
export const logout = async () => {
  await graphqlFetch(Logout, {});
  clearUnauthenticated();
  refetchStoreContext(undefined);   // ← direct call, not an invalidated key
  setUser(undefined);
};

Why (KDD)

Direct calls make "what refetches when" greppable — the cost is losing the automatic invalidation a cache-key system would give, which this app doesn't miss. Same principle as explicit composition: direct calls over subscriber/registry indirection. See kdd/state-management and kdd/explicit-composition.

Build step · widgets

In your WidgetsList, read useParams<{ storeId: string }>() — it is guaranteed present because the section renders inside StoreGuardLayout. Log currentStoreId() and switch stores: note it goes undefined during the switch (the guard shows its loading state) and comes back as the new store's id once context reloads.
