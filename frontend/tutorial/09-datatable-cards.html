Chapter 9

The DataTable — card view, column tabs & groups

Chapter 4 built the basic DataTable: headless TanStack under a hand-rolled <table>, sort/selection/ pagination controlled and page-owned, one typed extension (sortKey). This chapter covers the richer features added since — a card view, column tabs / card groups, row grouping, and per-breakpoint layout persistence — all built on the same rule: lean on TanStack where it genuinely owns the logic, extend it type-safely, keep the state the page's.

Why (KDD)

Everything here obeys one extension rule from kdd/table-state: an untyped display flag (card region, alignment, wrap-lines) goes in TanStack's meta bag; a convention that must carry a table-specific type (the sort-key union K, the card-group key union G) becomes a typed field on our Column<T, K, G>. Module augmentation of ColumnMeta can't carry K/G — it would degrade to string — so typed conventions can't live there.

The two view modes, at a glance

viewMode: 'table'
→
semantic <table> + tab strip
⇄
CardView
←
viewMode: 'card'

One toolbar button flips viewMode; a <Switch> in DataTable renders the <table> or the CardView. Both faces read the same column defs — a column says once (in meta / tabsAndCardGroups) how it should appear, and each face reads that. viewMode is itself a persisted config field (below), not page state.

Card view: a column opts a cell into a region

In card view each row becomes a card. A column declares where its cell lands via meta.card — a display-only flag, so it lives in TanStack's meta bag (augmented once in columnTypes.ts):

src/ui/elements/table/columnTypes.ts 
declare module '@tanstack/solid-table' {
  interface ColumnMeta<TData extends RowData, TValue> {
    align?: 'left' | 'right' | 'center';   // (ch4) an untyped display flag
    wrapLines?: number;                    // clamp body cells to N lines
    card?: { region: 'primary' | 'badge'; showLabel?: boolean };
  }
}
  • region: 'primary' — the big top-left title of the card.
  • region: 'badge' — the chip in the top-right corner.
  • No card — the cell falls into the card's single "secondary area" below the header (a wrapping label-value flow; each field captioned by its column's header).
  • showLabel: true — captions a primary/badge cell with a small muted label. The label text is the column's own header, so it isn't specified twice — useful for an otherwise-unlabelled cell (e.g. an editable input in the primary slot).

CardView reads those regions straight off the visible cells of TanStack's row model — no parallel data path, just a filter by region:

src/ui/elements/table/CardView.tsx 
const cellCardRegion = (cell) => cell.column.columnDef.meta?.card?.region;

// per row: split the row's visible cells by region
const inRegion = (region) => cells().filter(c => cellCardRegion(c) === region);
const secondaryCells = () => cells().filter(c => cellCardRegion(c) === undefined);
// primary → .cardPrimary (top-left), badge → .cardBadge (top-right),
// the rest → the secondary area. Same flexRender as the table cell.

Card view reuses the table's engine, not its markup

CardView takes the same table instance and calls table.getRowModel(), row.getVisibleCells(), row.getIsSelected() — selection, visibility and row-click all mirror the table exactly. It only changes where each cell is placed, via flexRender(cell.column.columnDef.cell, …). Column columnVisibility still applies — a hidden column doesn't appear on the card either.

Column tabs & card groups: one shape, two faces

A wide table can carry more columns than fit at once. A card group is a set of columns that presents as a tab in table view and a section in card view — one declaration, both faces (hence the field name tabsAndCardGroups). The page declares the groups as a typed const list:

src/ui/elements/table/columnTypes.ts 
export type TabAndCardGroup<G extends string> = {
  key: G;                    // what a column's tabsAndCardGroups entry must match
  labelKey: LocaleKey;         // i18n key — shown on the tab + the card group-row
  icon?: () => JSX.Element;    // a FACTORY: renders in many places at once
};

Why the icon is a factory, not an element

icon is () => <Icon/>, not a bare <Icon/>. The same icon renders in several places at once — the tab strip and one card group-row per card. A shared JSX element is a single DOM node that can only live in one place (it would end up on just the last card), so every render site calls the factory for its own node.

A column joins zero or more groups via its tabsAndCardGroups field — a typed field on Column<T, K, G>, not meta, because it carries the G key union (a typo is a compile error). The value is one of three things:

src/ui/elements/table/columnTypes.ts 
// A column that belongs to EVERY tab but is NOT itself part of card grouping
// (a row-identity anchor — the item name, the batch).
export const ALL_TABS = '__all_tabs__';

// A column's membership as stored on the def:
export type Membership = string[] | typeof ALL_TABS | undefined;

// Column's field is the TYPED version of that:
tabsAndCardGroups?: G[] | typeof ALL_TABS;
  • ALL_TABS (the bare const, not an array) — an anchor: shows in every tab in table view; in card view falls to the ungrouped area (unless it also has a meta.card region). Not a card group itself.
  • an array of group keys (e.g. ['supply', 'pricing']) — the column belongs to those card groups; a column may list several.
  • absent — the column is in no group; in card view it lands in the ungrouped area.

The membership tests are two tiny pure functions, used by both faces: 

// Does this column show in a given tab? ALL_TABS → any tab; array → if it lists it.
const membershipInTab = (m, tab) =>
  m === ALL_TABS ? true : Array.isArray(m) ? m.includes(tab) : false;

// The REAL card-group keys a membership names (ALL_TABS / absent → none).
const membershipCardGroups = (m) => Array.isArray(m) ? m : [];

Table view: a secondary visibility filter

When tabsAndCardGroups is wired the table shows a lightweight role="tablist" strip and renders only the active group's columns. This is a display-time filter, not a column filter: TanStack always holds the full column set (so order/visibility/sizing stay unambiguous — hiding a shared column is global), and the table simply <Show>s the header/body cells whose column is in the active tab. The table owns the active tab as an internal signal (defaulting to the first) — no active-tab state leaks to the page.

src/ui/elements/table/DataTable.tsx 
// A column shows in the active tab when its membership includes it OR ALL_TABS;
// with no card groups declared, every column shows.
const columnInActiveTab = (col) => {
  const cardGroup = activeTab();
  if (!props.tabsAndCardGroups || cardGroup === undefined) return true;
  return membershipInTab(col?.tabsAndCardGroups, cardGroup);
};

Card view: a section per group

In card view the same groups drive the card's secondary area. CardView makes two passes over the cells that have no explicit region: pass 1 — one row per declared group (led by the group's icon, its cells captioned by their headers), skipping groups with nothing visible; pass 2 — a final unlabelled row for cells in no real group (ALL_TABS anchors + un-annotated columns). An ungrouped table renders one flat row. A cell is "in a group" only via a real key — ALL_TABS never counts as a card group.

Card groups ≠ row grouping

A separate optional feature, rowGroup, collapses rows sharing a value under one expandable parent (e.g. all a stocktake item's batches). That's pure TanStack — getGroupedRowModel + getExpandedRowModel + per-column aggregationFn. Parent cells show a column's aggregate; the repo ships sharedOrMultiple (one shared value, else the MULTIPLE = "[multiple]" placeholder) and a date variant. Grouping on/off is a persisted config toggle (groupBy), like viewMode — not page state. Don't confuse it with card groups: card groups partition columns, row grouping collapses rows.

Layout persistence: three layers, per breakpoint

Column layout — columnOrder, columnSizing, columnPinning, columnVisibility, plus the view-level viewMode and groupBy — is controlled exactly like sort/selection: the page resolves it into one config and passes a setConfig; the table mirrors config into TanStack state and calls setConfig with the resolved next value for one field. The config shapes are TanStack's own state shapes — no remapping (kdd/type-safety).

createTableConfig is the app-glue that produces that config/setConfig. It resolves three layers per breakpoint band (base | compact), highest wins, per field:

default (the table's own defaults)
→
global (GraphQL blob)
→
user (localStorage)
→
resolved config
src/ui/elements/table/tableConfig.ts 
// Per FIELD, take it WHOLE from the first layer that provides it at THIS band.
// Bands don't share — a compact override never inherits base.
const pick = (key) => user?.[key] ?? global?.[key] ?? def?.[key];
return { columnOrder: pick('columnOrder'), columnSizing: pick('columnSizing'),
         columnPinning: pick('columnPinning'), columnVisibility: pick('columnVisibility'),
         viewMode: pick('viewMode'), groupBy: pick('groupBy') };
  • default — a table's non-fallback defaults (start-hidden/pinned). An unset field is simply omitted, and TanStack falls back to the columns prop (all visible, declaration order, auto widths).
  • global — a store-scoped globalTableConfigs blob fetched via GraphQL. Every table's config lives in one blob; each table narrows to its own tableId.
  • user — appData / localStorage, keyed by user + tableId. The only writable layer; setConfig writes here at the current band.

It's a store-scoped resource consumer (ch6)

The global layer is one createStoreScopedResource created once at module scope — so the singleton/dedup from chapter 6 is real: N tables share one lazy, store-keyed fetch, refetched on store change. Read via .noSuspense() so a pending first load never trips an ancestor <Suspense> or remounts a live table. Creating it inside createTableConfig would build a new singleton per table and defeat the dedup.

The column shape, end to end

A column now carries its identity, its typed extensions (sortKey, tabsAndCardGroups), and its display flags (meta) — each on the right axis: 

export type Column<T, K extends string, G extends string = never> = {
  c: ColumnIdentity<T>;                       // key | id | accessor+id — spelled ONE way, typed
} & Omit<IdentifiedColumnDef<T>, 'id'> & {   // TanStack's cell/header/meta/aggregationFn…
  sortKey?: K;                            // typed: the GraphQL sort field union
  tabsAndCardGroups?: G[] | typeof ALL_TABS; // typed: the card-group key union
};

From the showcase, two representative columns — an ALL_TABS anchor that's also the card's primary title, and a member of the details group shown as the badge:

src/ui-showcase/TableShowcase.tsx 
{
  c: { key: 'name' }, sortKey: 'name', header: 'Item',
  meta: { card: { region: 'primary' } },     // card view: the big title
  tabsAndCardGroups: ALL_TABS,               // every tab; anchor, not a group
  aggregationFn: sharedOrMultiple,           // row grouping: shared value or [multiple]
},
{
  c: { key: 'category' }, sortKey: 'category', header: 'Category',
  meta: { card: { region: 'badge' } },       // card view: the top-right chip
  tabsAndCardGroups: ['details'],             // tab "Details" (table) / section (card)
},

Build step · widgets

Give your WidgetsList table a card view. Add meta.card to two columns — a region: 'primary' title and a region: 'badge' chip — and confirm the table↔cards switcher lays them out. Then declare a TabAndCardGroup<WidgetGroupKey>[] of two groups (say info and stock), tag your columns' tabsAndCardGroups (keep the identity column as ALL_TABS), and check that the tab strip filters columns in table view and renders one section per group in card view. Finally wire createTableConfig({ tableId: 'widgets' }) into config/setConfig and verify a reorder or a hidden column survives a reload (user layer) and that resizing below the compact breakpoint follows its own band.
