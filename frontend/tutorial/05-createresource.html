Chapter 5

createResource, without remounting the screen

This is where the list gets its data. createResource re-fetches whenever its source signal changes — but reading a pending resource under <Suspense> tears the whole boundary down, which reads to the user as "the field unfocused while I was typing" or "the form reset when I toggled something." This chapter is the set of rules that stop that from happening.

Why this matters (KDD)

A remount is a data-fetch or routing event, never an interaction event. Typing, selecting, toggling, filtering and paginating must update the live DOM in place. The failure is transient (the subtree tears down and rebuilds within one interaction), so it must be prevented by construction, not caught after the fact. See kdd/solid-reactivity-pitfalls.

Rule 1 — refetch on change with a serialised source

The list resource's source is JSON.stringify(variables()), not the variables object. Two states with identical query content produce an equal string, so the resource does not refetch — e.g. adding an empty filter chip, which maps to the same effective filter, doesn't reflash the list.

src/sections/stocktakes/StocktakesList.tsx 
const [data, { refetch }] = createResource(
  () => JSON.stringify(variables()),          // ← source: a stable STRING
  async (serialised) => {
    const result = await graphqlFetch(Stocktakes, JSON.parse(serialised));
    if (result.kind !== "success") return undefined;   // failure handled globally
    return result.data.stocktakes;
  },
);

const rows = () => data()?.nodes ?? [];
const totalCount = () => data()?.totalCount ?? 0;

Crucially, the list reads data()?.nodes ?? [] directly — there is no <Suspense> wrapping the table. During a refetch, data() returns the previous value, so the rows swap in place and the table never remounts. Sorting, filtering and paging all just re-write the URL (chapter 4), which changes the source string, which refetches — with no flash.

Rule 2 — the sanctioned suspending read: initial load only

Suspense isn't banned — it's exactly right for a screen's first load, where there's no user state to lose. The detail view uses it, plus <Show keyed> so navigating to a genuinely different record gets a fresh subtree.

src/sections/stocktakes/StocktakeDetailView.tsx 
const [data] = createResource(
  () => ({ storeId: params.storeId, stocktakeId: params.stocktakeId }),  // refetch on route change
  async (variables) => { /* graphqlFetch(StocktakeDetail, …) */ },
);

return (
  <Suspense>                              // OK: initial load, no user state at risk
    <Show when={data()} keyed>             // keyed: a NEW record → fresh subtree
      {(node) => <Page> … </Page>}
    </Show>
  </Suspense>
);

The trap

Use <Show keyed> only for "a different record loaded." Never for "the same record got new field values" — that would remount and drop local state. Same for Suspense: reserve the suspending read (resource()) for initial load; a resource that refetches while a screen stays open must not suspend that screen's boundary.

Rule 3 — live-refetch-while-open: read without suspending

The hardest case: a resource that refetches while a form is open. The create modal shows a live "estimated line count" that recomputes as the user edits the form. This modal renders under AppShell's <Suspense> (there for lazy section chunks), so a pending read there would trip the fallback → remount the section → reset the form mid-edit.

The fix is to read via a state gate, never a suspending read:

src/sections/stocktakes/CreateStocktakeModal.tsx 
const [estimate] = createResource(
  () => (isBlank() ? null : JSON.stringify(form())),  // null source → no fetch
  async () => { /* count lines matching the form filters */ },
);

// Read WITHOUT suspending: gate on resource.state — NEVER `.latest`, which suspends
// on the first pending read (that IS the remount bug).
const estimatedLines = (): number =>
  estimate.state === "ready" || estimate.state === "refreshing"
    ? (estimate.latest ?? 0)
    : 0;

Why .state, not .latest

It's tempting to reach for resource.latest ("the previous value, kept during a refetch"). But .latest still suspends on the very first pending read — before there is any previous value. Gating on resource.state ("ready" or "refreshing" → the value; anything else → a fallback) never touches the boundary, first read or later. This subtlety is the whole point of the pattern.

The three cases side by side

Situation Read Wrapping Suspense?
List refetch on filter/sort/page data()?.nodes ?? [] none — swaps rows in place
Detail initial load resource() under <Suspense> + <Show keyed> yes — no state to lose on first load
Live estimate while a form is open state === "ready" | "refreshing" gate renders under one, so must not suspend it

Reflecting a mutation: refetch directly

Chapter 3's "refresh by direct call" shows up here too. After a successful batch delete, the list just calls its own refetch() — no cache key, no invalidation. 

const result = await graphqlFetch(DeleteStocktakes, { storeId, ids });
if (result.kind === "success" && !failed) {
  setSelectedIds([]);
  void refetch();                      // ← deleted rows disappear; direct call
}

Build step · widgets

Wire your WidgetsList resource keyed on () => JSON.stringify(variables()) and read data()?.nodes ?? [] straight into the DataTable — no Suspense. Then add a live "matching count" resource read through a state === "ready" | "refreshing" gate, and confirm (using the detect-remounts skill if you have it) that typing in a filter never remounts the table.
