Chapter 1

Codegen & the never-throwing fetch

The data spine. A .graphql file becomes a fully typed document with a query string and no runtime library; one function, graphqlFetch, runs it and returns a discriminated result you match on — it never throws.

Why home-baked, not Apollo/urql

The app deliberately keeps its own light GraphQL layer. Operations are plain .graphql documents, a custom codegen plugin turns each into a typed document (a query string plus phantom types), and a single hand-written graphqlFetch posts it over fetch. The graphql package is build-time only and never reaches the browser.

Why (KDD)

A cost study measured four alternatives. Our string-document approach ships the smallest bundle (9 KB gzip vs ~18 KB for urql) with zero per-request CPU overhead — normalising caches and request dedup are the reasons to reach for a client library, and this app doesn't need them (SolidJS reactivity composes the state). See kdd/graphql-client.

Step 1 — Author a document

Every operation lives in a .graphql file, co-located with the code that uses it. Here's the shape of a real one (the stocktakes list query), which our widgets query will imitate:

src/sections/stocktakes/stocktakes.graphql 
# Filter / sort / pagination are GraphQL input types so URL state maps
# straight onto them with no remapping (kdd/type-safety).
query stocktakes(
  $storeId: String!
  $filter: StocktakeFilterInput
  $sort: [StocktakeSortInput!]
  $page: PaginationInput
) {
  stocktakes(storeId: $storeId, filter: $filter, sort: $sort, page: $page) {
    ... on StocktakeConnector {
      __typename
      totalCount
      nodes { id stocktakeNumber status description comment stocktakeDate isLocked }
    }
  }
}

Build step · widgets

Create src/sections/widgets/widgets.graphql with a query widgets($storeId: String!, $filter: WidgetFilterInput, …) that selects a WidgetConnector with totalCount and nodes { id name category status }. Same shape as above.

Step 2 — Run codegen

There is no codegen.yml. A hand-written Node runner walks every src/**/*.graphql, introspects the live schema, runs the custom plugin, and writes a co-located <name>.generated.ts next to each source file.

codegen/run.cjs (abridged) 
const SCHEMA_URL = process.env.SCHEMA_URL || "http://localhost:8000/graphql";

// Introspect the live schema, then for each .graphql file emit a sibling .generated.ts
for (const file of walk(SRC_DIR)) {
  const outPath = file.replace(/\.graphql$/, ".generated.ts");
  const output = await codegen({
    schema: schemaAst,
    documents: [{ location: file, document: parse(content) }],
    plugins: [{ custom: {} }],
    pluginMap: { custom: require(PLUGIN_PATH) },  // codegen/plugin.cjs
  });
  fs.writeFileSync(outPath, output);
}

Run it with the npm script:

node codegen/run.cjs        # or: SCHEMA_URL=… node codegen/run.cjs
# package.json → "codegen": "node codegen/run.cjs"

Step 3 — What the plugin generates

The custom plugin (codegen/plugin.cjs) walks each selection set against the schema, so nullability and scalars are accurate. Per operation it emits three things: a Variables type, a Result type, and a const holding the query string typed as a TypedDocument. Per fragment it emits a reusable <Name>Fragment type. Here is a real before/after.

src/api/auth.graphql (input) 
query authToken($username: String!, $password: String!) {
  authToken(username: $username, password: $password) {
    ... on AuthToken      { __typename user { ...UserInfo } }
    ... on AuthTokenError { __typename error { description } }
  }
}
fragment UserInfo on UserNode { __typename userId username … }
src/api/auth.generated.ts (output — abridged) 
import type { TypedDocument } from "./graphql";

// Fragment → a reusable type, referenced wherever it's spread.
export type UserInfoFragment = { __typename: "UserNode"; userId: string; … };

export type AuthTokenVariables = { username: string; password: string };

// Inline fragments on a union → a DISCRIMINATED union, __typename in each branch.
export type AuthTokenResult = {
  authToken:
    | ({ __typename: "AuthToken"; user: UserInfoFragment })
    | ({ __typename: "AuthTokenError"; error: { description: string } });
};

// The document itself: the query as a plain string, typed via `as`.
export const AuthToken = {
  query: "query authToken($username: String!, …) { … }",
} as TypedDocument<AuthTokenResult, AuthTokenVariables>;

The key trick: TypedDocument carries types with no runtime cost

The document is just an object with a query string. Its result and variables types ride along as phantom fields — declared in the type, never assigned at runtime — so the string knows exactly what it takes and returns.

src/api/graphql.ts 
export interface TypedDocument<TResult, TVariables> {
  query: string;
  __result?: TResult;      // phantom — carries the result type only
  __variables?: TVariables;  // phantom — carries the variables type only
}

Step 4 — Run it: graphqlFetch

One async function ties a typed document to its variables. It infers both from the passed document, so a query can only be called with its own variables and yields its own result. It never throws — it returns a discriminated GraphqlResult you match on, Rust-style.

src/api/graphql.ts 
export type GraphqlResult<TResult> =
  | { kind: "success"; data: TResult }
  | { kind: "unauthenticated" }
  | { kind: "unexpectedError" }
  | { kind: "graphqlError"; message: string; errors: GraphqlErrorItem[] };

export async function graphqlFetch<TResult, TVariables>(
  document: TypedDocument<TResult, TVariables>,
  variables: TVariables,
  options: FetchOptions<TResult> = {},
): Promise<GraphqlResult<TResult>>
Result kind When What the caller does
success data came back use result.data (fully typed)
unauthenticated a Unauthenticated GraphQL error nothing — the global re-login flow is tripped for you
unexpectedError connection fail, bad HTTP, unusable body, or (by default) any GraphQL error nothing — the global error modal is tripped; stay in your loading phase
graphqlError only if you passed returnGraphqlErrors handle the error yourself

Notice what the default gives you: every call site is just a happy path. You check for success and return early otherwise; the error is already on global state and a modal is already showing. Auth is cookie-based — the fetch sends credentials: "same-origin" with no token header.

how a fetcher reads at the call site 
const result = await graphqlFetch(Widgets, { storeId, filter, sort, page });
if (result.kind !== "success") return undefined;  // handled globally
return result.data.widgets;                       // typed as WidgetConnector

Two opt-in escape hatches

Occasionally the default isn't what you want. Two flags cover those cases:

  • returnGraphqlErrors: true — hand GraphQL errors back to you as { kind: "graphqlError" } instead of promoting them to the global modal.
  • mapSuccessToError — inspect a well-formed payload and promote a bad in-band value to the global modal. The transport succeeded, but a union branch "that should never happen" came back. Real example, the detail view: 
const result = await graphqlFetch(StocktakeDetail, variables, {
  mapSuccessToError: (d) =>
    d.stocktake.__typename === "NodeError" ? d.stocktake.error.description : undefined,
});
// A NodeError (e.g. bad id) becomes an unexpectedError and never reaches the view.

Build step · widgets

Run node codegen/run.cjs and confirm widgets.generated.ts appears with WidgetsVariables, WidgetsResult, and the Widgets document. Then write a tiny fetcher that calls graphqlFetch(Widgets, …) and returns undefined on anything but success.
