Chapter 6

Store-scoped global caches

The finale ties chapters 3 and 5 together. Some lookups — master lists, locations, categories — are needed all over the app, always for the current store, and read by many components at once. createStoreScopedResource is the reusable factory for exactly that: a lazy, store-keyed, de-duplicated global cache.

A note on the name

You may have heard this called "storeScopedContext." There is no such symbol — the real thing is createStoreScopedResource. It's a resource, not a context; "scoping to the current store" is done by depending on the module-level currentStoreId() accessor from chapter 3.

What it gives you, for free

It builds a createResource inside a lazy createRoot singleton. That single construction buys three behaviours:

  • Lazy — the resource is created on the first read. A screen that never reads the cache never creates or fetches it.
  • Store-aware — the resource's source is currentStoreId, so it refetches automatically whenever the store changes. The key is the store id — no hand-rolled comparison.
  • De-duplicated — one shared singleton plus createResource's own single-flight means N consumers (say 30 table cells reading the same cache) cause one request, not 30. No debounce needed.
src/api/storeScopedResource.ts (the core) 
export function createStoreScopedResource<T>(
  storeId: () => string | undefined,               // e.g. currentStoreId
  fetcher: (storeId: string) => Promise<T[] | undefined>,
): StoreScopedResource<T> {
  let instance;                                        // lazy singleton
  const build = () => createRoot(() => {              // root → clean disposal
    const [resource, { refetch }] = createResource(
      storeId,                                        // source → refetch on store change
      async (id) => (await fetcher(id)) ?? [],
    );
    return { suspends, noSuspense, loading, refetch };
  });
  return {
    suspends:   () => (instance ??= build()).suspends(),   // first read arms the fetch
    noSuspense: () => (instance ??= build()).noSuspense(),
    loading:    () => (instance ??= build()).loading(),
    refetch:    () => (instance ??= build()).refetch(),
  };
}

The two named reads (chapter 5, generalised)

The factory never exposes the raw resource. Instead the consumer chooses its read behaviour by name — so you can't accidentally suspend. This is chapter 5's rule baked into the API surface.

src/api/storeScopedResource.ts 
suspends: () => resource() ?? [],          // SUSPENDS on first pending read — use only
                                          // where a <Suspense> fallback is the UX you want

noSuspense: () =>                          // NEVER suspends. gate on .state, not .latest.
  resource.state === "ready" || resource.state === "refreshing"
    ? resource.latest                     // keeps the prior list during a refetch (no flash)
    : [],

Same subtlety as chapter 5

noSuspense gates on resource.state, not resource.latest — because .latest still suspends on the first pending read. Naming the two reads means a consumer decides suspend-or-not explicitly, rather than having to remember the behaviour of a single data().

A real consumer

Every cache is a module-scope singleton so the dedup is real — every consumer reads the same instance. Master lists are a one-liner:

src/api/masterListsResource.ts 
export const masterListsResource = createStoreScopedResource<MasterList>(
  currentStoreId,
  async (storeId) => {
    const result = await graphqlFetch(MasterLists, { storeId });
    return result.kind === "success" ? result.data.masterLists.nodes : undefined;
  },
);

Consumed in the create modal — note the .noSuspense() read, inside a form: 

<Combobox
  items={masterListsResource.noSuspense()}   // never suspends the open modal
  loading={masterListsResource.loading()}
  … />

Build step · widgets

Add widgetCategoriesResource = createStoreScopedResource(currentStoreId, …) in src/api/. Read .noSuspense() from several places in your widgets UI at once and confirm — in the network tab — that they cause a single request per store, and that switching stores refetches exactly once. That's the whole vertical: codegen → fetch → auth/store gating → URL-driven list → non-suspending resources → shared store-scoped caches.

The whole model, in one breath

A codegen plugin makes typed documents; one never-throwing graphqlFetch runs them and handles errors globally; global state is module-level signals plus explicit refetches; the URL drives list variables; resources refetch on change without ever suspending a live screen; and shared lookups are lazy, store-keyed, deduplicated caches. No provider tree, no client cache, no cache keys — just SolidJS reactivity and a handful of deliberate rules.
