First slice of building out Variants/Bundling/Ancillary/Ledger: the Variants tab's **presence** is now wired to `isCentralServer()` (`detail/itemDetailTabs.ts`, colocated + unit-tested — `CAT-05.1`/`.2`), reusing the exact pattern `settings/sectionVisibility.ts` already proved out (a pure function over server-role/permission, `<Show>`-gated in the view). ## Update 2026-07-27 — Ledger tab

Second slice: the Ledger tab is now fully built (`ItemLedgerPanel.tsx` + `itemLedger.graphql` + `itemLedgerNav.ts`), closing `CAT-04.22`/`.24`/`.41`/`.42` and most of `.23` (source-document navigation). Server-paginated, fixed most-recent-first (the endpoint has no sort input); filters by document type, status, and a new date-_time_ range control; row-click navigates by invoice type.

- **`FilterDateTimeRange`** added to `FilterBar.tsx` — two independent `DateTimeField`s (From/To), since no shared range primitive picks time yet (unlike `FilterDateRange`'s date-only corvu range calendar). Documented in `src/ui/docs/UI_ELEMENTS.md`.
- **Row navigation (`itemLedgerNav.ts`, new logic — nothing like it existed anywhere in the app)**: routes `OUTBOUND_SHIPMENT`/`INBOUND_SHIPMENT`/`CUSTOMER_RETURN`/`PRESCRIPTION` to their existing detail routes; `INVENTORY_ADDITION`/`INVENTORY_REDUCTION` never navigate (spec). `isExternal` (PO-born inbound shipment) does **not** change the route — `InboundShipmentDetailView` already renders both on the same route, branching internally (the schema doc-comment's "separate routes" describes the _reference_ app, not this rewrite).
- **Known gap, not a spec exclusion**: `SUPPLIER_RETURN` and `REPACK` ledger rows don't navigate — neither has a built route in this app yet. Revisit once those verticals exist; `.23`'s case bullet notes this explicitly so it isn't mistaken for a regression.
- **Codegen backend mismatch (flag below) no longer reproduces** — `pnpm codegen` against the default `:8000` now succeeds repo-wide (72 files, byte-identical except the new `itemLedger.generated.ts`); `ItemVariantNode`/`BundledItemNode`/`AncillaryItemNode` all resolve there too. Worth re-confirming before the Variants/Ancillary slices assume it's still needed, but as of this pass a scoped `:8890` runner is no longer necessary.

## Update 2026-07-27 — Ancillary items tab

Third slice: the Ancillary items tab is now fully built — read-only listing on every site, central-only add/edit/delete via the S5 modal. Closes `CAT-08.1`-`.16` in full.

- **`ancillaryItems.graphql`** (own query, refetches independently of `itemDetail.graphql`) + **`ancillaryItemMutations.graphql`** (`upsertAncillaryItem`/`deleteAncillaryItem` under `centralServer.ancillaryItem`, mirroring `helpDocumentMutations.graphql`'s central-gate shape). A GraphQL-codegen gotcha worth flagging: querying only ONE inline fragment on a multi-member error interface (e.g. just `... on AncillaryMaxDepthExceeded`) makes the plugin emit a type that assumes the error is ALWAYS that member — every other typename in the union needs its own `... on X { __typename }` stub (even with no extra fields) to get a real discriminated union back. `locations.graphql` already does this correctly; the first draft of `ancillaryItemMutations.graphql` didn't and had to be fixed.
- **`ancillaryItemEdit.ts`** (+ tests) — form validity, `buildUpsertInput`, `saveRejection`/`rejectionMessage` (typed union → the case's own copy for Duplicate/Cycle/MaxDepth; `DatabaseError`/`InternalError` fall back to the server's raw `description`, untranslated — confirmed against the real open-mSupply app's `useUpsertAncillaryItem.ts`, which does exactly this; no generic "failed to save" locale key needed), `formatRatio` (ported from the real app's `ratio.ts`).
- **`AncillaryItemEditModal.tsx`** — mirrors `LocationEditModal.tsx`'s shape (Dialog, reseed-in-place, never remount). `ItemSearch` (`src/domain/item/ItemSearch.tsx`, already generic) supplies the ancillary-item picker, `excludeItemIds` covering the principal + every existing link. Save & Next is add-mode only (ui-surface S5), resetting the draft in place rather than the real app's key-bump remount trick.
- **`ItemAncillaryPanel.tsx`** — the tab's table + empty state + delete confirmation. The central-only "Add ancillary item" trigger lives in the page header (a page action) rather than inside this panel — this app has no portal mechanism, so the modal's open/edit state is owned by `ItemDetailView.tsx` itself and passed down as a controlled prop (mirrors `PrescriptionDetailView.tsx`'s top-level edit-state pattern).
- Self-link / non-positive-ratio / missing-item rejections are non-typed top-level GraphQL errors (`contract.md`) but are also client-guarded already (picker exclusion, Save disabled until both ratio sides are positive) — no `returnGraphqlErrors`/special parsing needed; they (and a stray `Forbidden`) fall through to the existing global-modal handling for free.
- **Live-verified** end-to-end against a running central-server session (`:8890`, via a temporary second dev instance proxied there — the running `:3005`/`:8000` instance was left untouched): the Variants tab and every Ancillary affordance appear; add (search → pick → ratio → Save) creates the link and shows it in the table; selecting the row reopens the modal pre-filled with the item picker locked; editing the ratio and saving persists the change; delete asks for confirmation, Cancel leaves the row intact, and confirming removes it back to the empty state. Duplicate/cycle/depth-exceeded rejections weren't separately probed live (they need multi-item chain setups) — covered by `ancillaryItemEdit.test.ts` instead.

## Update 2026-07-27 — Variants + Bundling tab

Fourth slice, the last big piece: the Variants tab is now fully built — a card per variant (`ItemVariantCard.tsx`, built on the new shared `DetailCard` component), full create/edit/delete via the S3 modal, and the two-sided Bundling section (Bundle with / Bundled on) via the S4 modal. Closes `CAT-05.3`-`.15`, `.20`-`.28` and `CAT-06.1`-`.5`, `.9`-`.18`.

- **`DetailCard`** (`src/ui/layout/Detail/DetailCard.tsx`) — a titled card with header actions, extending the `DetailContainer`/`DetailSection`/`DetailRow`/`RecordNameHeader` family with the one shape it didn't cover (several records of the same kind stacked as cards). Landed in its own PR ahead of this one (per instruction: new shared components get a separate PR from the feature that first consumes them).
- **`itemVariants.graphql`** (own query, mirrors `ancillaryItems.graphql`'s refetch-independent pattern) — parametrised by `itemId` alone, so it doubles as S4's "this item's variants" fetch when a different item is picked in the Bundled-item modal. Also carries `itemVariantLocationTypes`, duplicating `locations.graphql`'s `locationTypes` field under a distinct operation name (operation names are global to codegen) rather than a cross-vertical generated-file import. **`itemVariantMutations.graphql`** — `upsertItemVariant`/`deleteItemVariant`/`upsertBundledItem`/`deleteBundledItem` under `centralServer.{itemVariant,bundledItem}`, with the same "every union member needs its own `{ __typename }` stub" codegen care as `ancillaryItemMutations.graphql`.
- **Packaging rows are fixed at three (Primary/Secondary/Tertiary), never added to or removed** — confirmed by auditing the real open-mSupply app's `useItemVariant.ts`/`ItemPackagingVariantsTable.tsx` live: `packagingLevel` is rendered read-only there too, and there is no add-row affordance anywhere. rules.md's "starting point, not a rule" language describes the row _set_, not a licence to build add/remove UI that the reference app itself doesn't have — matched as-is rather than over-built.
- **`itemVariantEdit.ts`/`bundledItemEdit.ts`** (+ tests) — form validity (name + every packaging row's pack size/volume-per-unit **positive**, the client mirror of the server's `LessThanZero` guard), `buildUpsertInput` (packaging as a full-replacement set), `saveRejection` (the one typed rejection, a duplicate name, mirrors `locationEdit.ts`'s `UniqueValueViolation` shape exactly), and `isVariantDisabled` — the bundled-item candidate guard, symmetric in **both** nesting directions (`bundledItemVariants.length > 0` OR `bundlesWith.length > 0` OR already-bundled-to-this-principal), which is stricter than the reference app's own `BundledItemModal.tsx` (that only checks the candidate's `bundledItemVariants`, not `bundlesWith`) — grounded in this vertical's own contract.md, which documents the no-nesting rule as bidirectional.
- **`ItemVariantEditModal.tsx`** (S3) — two-column (`FormColumns`/`FormColumn`, the `InsuranceModal.tsx` precedent for a form-shaped Dialog body): Name/Location type (`Combobox`, temperature-range label)/Manufacturer (`NameSearch` role="manufacturer")/VVM type (vaccine items only) · a hand-rolled packaging grid (own CSS grid — three fixed rows don't warrant `DataTable`'s row/sort/pagination machinery). **`BundledItemModal.tsx`** (S4) — `ItemSearch` (excluding this variant's own item) → the chosen item's variants via the same `itemVariants` query → Ratio, pre-filled 1. Create-only (no row-click-to-edit; see the scope note below).
- **`ItemVariantCard.tsx`** — the variant's read-only field set (`LabelledValue`, matching the General/Store tabs' D67 convention, not `DetailRow`) + a read-only packaging table + the Bundle-with/Bundled-on sections, each self-contained (owns its own delete-confirm/bundle-modal state locally rather than lifting it to the panel). **`ItemVariantsPanel.tsx`** — own query/refetch, `CardGrid` of cards, controlled add/edit-modal state from `ItemDetailView.tsx` (the "Add variant" trigger is a page-header action, same reasoning as Ancillary's S5).
- **Scope decision, not an oversight**: bundle rows have Add + per-row Delete only, no row-click-to-edit — ui-surface.md's S4 never asks for one, unlike the reference app (which does support it). `CAT-06.6`-`.8` (Edit bundle) stay `(pending)` in the case file, called out explicitly rather than silently closed.
- **Bug found + fixed during live verification**: the Manufacturer `NameSearch` field initially showed blank after picking a name — `onSelect` was only updating the draft's bare `manufacturerId` string, never the `NameOption` node `NameSearch`'s `selected` prop actually needs to render a label (an async picker has no client list to resolve an id against). Fixed by tracking the picked `NameOption` directly in a signal (seeded once from a by-id fetch on edit, via `domain/name/nameResource.ts`'s `fetchNameById` — the same "resolve before load" need `LocationEditModal.tsx`'s location type has).
- **Live-verified** end-to-end against a running central-server session (temporary second dev instance proxied to `:8890`, `:3005`/`:8000` left untouched): create a variant with all fields + packaging (Manufacturer/Location-type pickers both confirmed against real trading-partner/location-type data) → card renders correctly; bundle it to a second variant on a different item → both sides confirmed (principal's "Bundle with" row + the paired variant's "Bundled on" inverse-ratio row + link navigation) → "Add bundled item" correctly disabled with the `messages.cannot-bundle` caption on the bundled side → delete the bundle row (confirm dialog, correct message) → both sides clear → delete each variant (confirm dialog, correct message) → back to empty state. Zero console errors throughout.
