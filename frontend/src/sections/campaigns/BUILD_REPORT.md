> **Addendum (2026-08-18).** The selection delete described below (n independent `deleteCampaign` calls, partial success as the norm) has been replaced by the **atomic `deleteCampaigns`** mutation (open-msupply branch `campaigns-atomic-delete`): the selection deletes in full or not at all, and a refusal re-reads the register and prunes vanished rows from the kept selection. Candidate refinements 1–3 below are decided and folded into the spec (refuse-at-click recorded in `ui-surface.md`; the `messages.deleted-campaigns` citation resolved per D21; the required-name guard added to `validation.md`'s sanctioned list). The rest of this report stands as the record of the original build run.

**Target stack:** SolidJS + Vite; shared component library `src/ui/`, every slot resolved through the roles in [`spec/ui-standards/components.md`](../../../spec/ui-standards/components.md).

Scoped build of the campaigns vertical from [`spec/campaigns`](../../../spec/campaigns/README.md) (authored on `spec/campaigns`, which this branch is stacked on). The vertical is one screen — the central server's campaign register at `manage/campaigns` — plus its create/edit dialog and a delete confirmation. Types generated by `pnpm codegen` against the live central server on `:8890` (`SCHEMA_URL` override; `:8000` is the default and was not used). The codegen pass rewrote no other vertical's `.generated.ts`, which is a C7 signal in itself: the live schema still matches the pinned one.

**Gates: all three green.** `pnpm check` · `pnpm test` (1441 tests, 145 files, including 36 new campaign tests) · `pnpm build` (the section is its own chunk, `CampaignsList` 9.29 kB / 3.28 kB gzip).

## Built

- **S1 register** (`CampaignsList.tsx`) — the standard list screen: `Page` + `Header`(`Breadcrumb` / `HeaderButtons`) + `DataTable`, which owns its own toolbar, pager, and selection action bar. Columns Name (sortable, the default ascending sort) · Start date · End date, both dates rendered by the shared date cell and blank when unset. Server-paginated, page size 20, reporting the register's whole total. Sort/page state URL-backed via `useUrlQueryState`. Row click opens the editor — there is no detail screen.
  - **Three spec'd deviations from the standard list**, each deliberate: **no filter bar** (the `filters` slot is left unfilled — `CampaignFilterInput.name.like` is declared and silently ignored by the server, so there is no search to offer), **no Export** action, and **no sort on either date column** (`CampaignSortFieldInput` has only `name`, so the generated sort-key union is the literal `'name'` and a date column naming a key would not compile).
  - **Exactly one sort entry is always sent.** Omitting `sort` orders by opaque id, and a multi-entry list resolves to its _last_ entry — both contract wire traps. `campaignVariables` truncates to the first entry and falls back to the default, so neither trap is reachable even from a hand-edited URL.
- **S2 editor** (`CampaignEditModal.tsx`) — one `Dialog` for create and edit, because they are the same whole-record write; the draft **is** the generated `UpsertCampaignInput` and the id is client-supplied (`generateUUID()` on create). Three `FieldRow`s: Name (`TextField`, required, trimmed as the field is left) · Start date · End date (`DateField`, each optional, independently clearable, neither bounded by the other). Footer is `CancelButton` + `DialogSaveButton` — **Save, not OK** ([D55](../../../spec/DIVERGENCES.md)) — inert while Name is blank/whitespace, busy while saving. Lifecycle is the shared dialog contract ([D22](../../../spec/DIVERGENCES.md)): stays open while in flight, closes on success, stays open on rejection with the entered values preserved and the message in an `Alert` on the inline-start of the actions row.
- **S3 delete** (`DeleteCampaignsAction.tsx`) — the register's only bulk action, in the table's selection footer. `Dialog` with confirm → deleting → error phases (not `ConfirmDialog`, which closes on confirm and so cannot hold D22's error phase). Count-pluralised permanence notice, danger OK. Deletion is _n_ independent `deleteCampaign` calls with no transaction, so partial success is handled as the norm: all deleted → rows leave and the selection clears; any refused → the generic could-not-delete notice, the register re-read so the ones that went are gone, and **the selection deliberately kept**.
- **Picker cache invalidation** — every successful save or delete calls `campaignsResource.refetch()` (`src/domain/campaign`) alongside the register's own refetch, so a deleted campaign stops being offered by the campaign-or-program pickers and a renamed one is offered under its new name (`.27`). This is the one place the register reaches outside itself.
- **Wiring (additive only)** — `src/App.tsx` gains `'manage/campaigns': campaignsRoutes`; the `manage/campaigns` nav destination and its `central` capability gate already existed in `src/nav/navConfig.ts` and were not touched. `Alt+N` registered once for the screen via `createAddAction`, carried as a badge by both the header button and the empty-state ghost.
- **No new locale keys.** Every key `ui-surface.md` cites resolved verbatim in `src/intl/locales/en/`, plural variants included (`messages.confirm-delete-campaigns_*`, `messages.deleted-campaigns_*`). Nothing added to `fr/` or `ar/`.
- **Testids** — a Campaigns section added to [`e2e/TESTIDS.md`](../../../e2e/TESTIDS.md) contracting the screen-specific ids (`new-campaign-button`, `campaign-edit-modal`, `campaign-name-input`, `campaign-start-date-input`, `campaign-end-date-input`, `campaign-save-error`, `campaigns-cant-delete`); everything else is a shared id the library emits.

## Flags

- **⛔ roles used: none.** Every role `ui-surface.md` names resolves to a built (✅) or by-composition (🔶) component: standard list screen 🔶 · labelled action button `Button` · breadcrumbs `Breadcrumb` · data table `DataTable` · list pagination `Pagination` (inside the table) · empty state `EmptyState` (via the table's `empty*`) · bulk-action bar 🔶 (the table's own selection footer + a page-composed Delete) · modal dialog `Dialog` · detail container `DetailContainer` · vertical stack `Stack` · labelled field row `FieldRow` · short text `TextField` · date `DateField` · modal footer buttons `CancelButton`/`DialogSaveButton` · inline banner `Alert` · confirmation dialog (composed on `Dialog`, see below).
- **`ConfirmDialog` could not be used for S3.** The packaged confirm runs `onConfirm` and closes in the same call, so it cannot stay open while the deletes are in flight or hold the could-not-delete phase that D22 requires. Composed on `Dialog` instead — the same choice the reference vertical's delete action made. Worth a registry note if a third vertical repeats it.
- **DIVERGENCES honoured:** [D21](../../../spec/DIVERGENCES.md) (no toast — closure + the refreshed register is the whole success signal), [D22](../../../spec/DIVERGENCES.md) (dialog submit lifecycle, both dialogs), [D55](../../../spec/DIVERGENCES.md) (icon-less **Save** in the editor footer; **OK** only in the confirmation, where the action genuinely isn't a save).
- **`messages.deleted-campaigns` is deliberately NOT rendered.** `ui-surface.md` S1 cites it for the all-deleted case, but D21 removes exactly that announcement — and the same document says so two sections later ("closure and the register refreshing are the confirmation, never a toast"). The key stays in the catalogue unused, as the current app's. See candidate refinements.
- **`UniqueValueViolation.field` is not selected.** Its `UniqueValueKey` can only be `name` for this input, and naming the member in an inline fragment makes this repo's codegen collapse the whole error type onto that one member (so `error.__typename` narrows to a single literal and a comparison against any other member becomes a type error). The duplicate is identified by `__typename` instead; the reasoning is in the `.graphql` file.
- **The `createResource` read-safety gate is satisfied by the `.state` gate, not `.latest`.** The register's read is `state === 'ready' || 'refreshing' ? latest : undefined` — the binding form in [`kdd/solid-reactivity-pitfalls`](../../../kdd/solid-reactivity-pitfalls/draft-kdd.md#no-remounts-on-interaction). It matters here and not only in theory: the delete confirmation stays open in its could-not-delete phase _while_ the register re-reads behind it, and a suspending read there would detach the open native `<dialog>` and lose its backdrop. Note the reference vertical (`StocktakesList`) still reads `.latest` alone — this build follows the KDD, not the reference, where the two disagree.
- **Three `solid/reactivity` lint warnings, deliberate** — both dialogs read a prop once on mount (`props.campaign` to seed the draft, `props.selectedIds().length` to snapshot the count) precisely so a rejected save keeps what the user typed and the confirmation's count can't shift behind the dialog. Each is mounted only while open, so there is nothing to react to. The reference vertical's delete action carries the identical warning for the identical reason.
- **C2 real-backend leg: covered, no CI home.** The probe that exercised the shipped operations lives in the run's scratchpad, not the repo — there is still no CI tooling for C2, so this report is the record. Nothing was mocked to make a behavioural claim.
- **⚠️ VERIFY items encountered: none.** The spec carries no open flags.

## Decisions the spec should make (candidate refinements)

1. **The permission mirror's shape.** `ui-surface.md` says the change actions are "mirrored as standing capability", and `validation.md` offers two sanctioned treatments: hide/disable the affordance, or refuse at the click with the global permission-denied modal. This build chose **refuse at the click** — every change here is fired from a control that opens a dialog, which is the case that standard explicitly covers ("spares the user a multi-step flow the server would only reject at the final write"), and it keeps the register visually identical for every reader. The alternative (withhold the New campaign button and the selection column) is equally defensible. The spec should say which. Unverified either way: probing ran as an all-permission admin, so the refusal was never observed — the same gap the spec README carries for the server-side denial.
2. **`messages.deleted-campaigns` vs D21** — S1 cites a success message the divergence removes. Either drop the citation or record why this list announces what no other list does.
3. **The required-name guard is still outside the sanctioned list.** `ui-standards/validation.md` § deliberate UI-only guards does not include it, and this build ships it (the Save button's gate) because it is the app's only stop against a server that accepts a blank name. Carried from the spec README as a decision for a person; the build did not edit the shared standard to make itself consistent.

## Follow-ups

- **A deterministic `e2e/` suite for `manage/campaigns`** — the durable home for the eleven behaviours above that only a running UI can assert (columns, empty state, both dialogs' lifecycles, the count-pluralised confirmation, the partial-delete notice). The testid contract is already in `e2e/TESTIDS.md`; the suite needs a central-server fixture, which the current hermetic stack does not obviously provide.
- **An exploratory workflow** at `exploratory/workflows/campaigns.md` — none exists; the case is the walk until one is written.
- **The six backend gaps** in [`contract.md`](../../../spec/campaigns/contract.md#backend-gaps--capabilities-the-frontend-needs) are still unfiled upstream. The two that shape this screen: `name.like` is ignored (so the register can offer no search — the reason the filter slot is empty), and the out-of-order-dates rejection has no typed member (so the editor has to read `extensions.details`). Both are worked around here, neither is fixed.
- **`OMS-REG-SMV-09` is defined twice** (tmf-testing "Validate Backdating Prescriptions" vs `spec/stock-movements/cases/`). Pre-existing, untouched by this build, and cheap to fix while that id is still pending sign-off — flagged in the PR body, not this vertical's problem.
