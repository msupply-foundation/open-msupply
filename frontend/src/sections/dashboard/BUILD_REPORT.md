# Build report — dashboard

**Target stack:** SolidJS + Vite; shared component library `src/ui/` resolved through [`spec/ui-standards/components.md`](../../../spec/ui-standards/components.md).

Regenerated from `spec/dashboard/` (scoped `/spec-build dashboard`). One screen (S1) mounted at both the store root `/` (the landing screen) and the `dashboard` nav destination. Wire surface: the six split count queries in `dashboardCounts.graphql`; the display-gate preferences ride on the shared guard-3 `storeContext` query (no new wire fields — the `PreferencesNode` fields were already present). Gates green: `pnpm check`, `pnpm test` (596 total; 46 dashboard across 5 files), `pnpm build` (DashboardPage = its own lazy chunk, 14.43 kB / **3.85 kB gzip**).

**The dashboard owns the plugin-region semantics** (branch `448-dashboard-plugin-semantics`): how contributions merge with built-ins and how suppression by published id behaves — the published-id tree (`DASHBOARD_IDS`) plus the pure, unit-tested `mergeRegion` in `regions.ts` (deterministic anchor/order/id placement, suppression, missing-anchor diagnostics). OMS-REG-DB-02 (+ OMS-REG-DB-01.58) are covered at the logic level.

The **render integration** was deferred to the plugins vertical and has now landed with it (`#248` PR 3): `PluginRegion.tsx` mounts each region — the card grid, each widget's panel column, each panel's stat list — by feeding `visibleContributions` + `regionBuiltIns` into `mergeRegion` and rendering the plugin entries through `PluginRegionOutlet`; `DashboardPage` guards every built-in with `shows(id)` against `suppressedPieces()`, so the suppression cascade falls out of the page's nesting. The deferral's two reasons were honoured, not overridden: built-ins stay explicit JSX (no `<For>` over them, so no count update can remount a stat), and the contributions that _do_ come from a merged list come from a single `createMemo` per region. Contributions render at each region's tail, in merged order; interleaving BETWEEN built-ins remains out of scope (see the candidate refinement).

## Flags

- **C2 (real backend):** no CI tooling exists for the real-backend leg. Every count value is server-computed and wired verbatim; the client-side logic (gates, links, thresholds, panel states, region semantics) is covered at the logic level. The spec's validation notes record live verification of the counts.
- **A plugin stat shares its panel's loading/error state.** The stat region is the last child of the panel's stat LIST, and `StatsPanel` replaces that whole list while its own count query is loading or failed — so a contributed stat is absent until the panel's (unrelated) counts resolve. Consistent with ui-surface S1's "contributions adopt the owning screen's region geometry", but in tension with sdk-contract's "a dashboard stat owns its own loading/error state": a `Forbidden` on the HOST's count query currently hides the plugin's stat too. Fixing it means `StatsPanel` rendering the region outside its state switch — a library change, deliberately not taken in the render-integration PR. Widget- and panel-level regions are unaffected (no such switch above them).
- **`regionBuiltIns.ts` restates the page's structure.** `mergeRegion` needs each region's sibling ids in render order with their hidden flags, and the page's built-ins are explicit JSX, so the two can drift. Guarded by `regionBuiltIns.test.ts`: every published id must appear in exactly one region. A built-in added to the page without a home there fails the suite.
- **Stock-level links (item catalogue):** the six filtered stock-level stats (out-of-stock all / recently-used, at-risk, low-stock, high-stock, overstocked) link into `catalogue/items` filtered to their counts; total items + the panel title stay unfiltered. The dashboard conforms to the items list's **own** URL filter contract (`ItemsListFilter`: the `lens` stock-status enum + `atRisk` + `min/maxMonthsOfStock`) — the list owns its encoding and expands the lens to the wire `ItemFilterInput` itself; `spec/dashboard/contract.md § navigation correspondence` records this vocabulary. Only the customer-requisition stats remain on an unfiltered placeholder (requisitions vertical unbuilt); the internal-order draft stat now filters `status=DRAFT` via the internal-orders list's own contract.
- **Internal vs external inbound links (contract › navigation correspondence):** ~~not expressible~~ — the inbound list has since shipped its origin `kind` URL filter, and the **external** panel's links (title + stats) now carry `kind=fromPurchaseOrder` (exactly the PO-linked count set). Still open for the **internal** panel: "internal" = `manual` ∪ `fromInternalOrder`, and the single-select `kind` has no value covering both, so internal links remain window/status-only (recorded fallback).
- **Order more (OMS-REG-DB-01.56):** resolved — the shortcut now opens the internal-orders vertical's own create flow (permission gate → recent-stocktake warning gate, spec/internal-orders AC-C1/C5 → `CreateInternalOrderModal`), navigating to the created order's detail. The warn preference rides the guard-3 store context; the insufficiency check and both dialogs lazy-load on first use.
- **Cross-section create-flow imports:** the New inbound / New outbound shortcuts lazily import `CreateInboundShipmentModal` and `CustomerSearchModal` from their owning sections (self-contained modals; loaded on first use). If more consumers appear, hoist to `src/domain/`.
- **Codegen drift in other verticals (C7):** running `pnpm codegen` regenerated `customer-returns` and `outbound-shipments` generated files against the newer pinned schema; those regenerations were reverted (out of scope). Those verticals need a regen + filter-map pass on their next build.
- **Expiring-soon link boundary:** resolved — the soon link now spans tomorrow…today+30, exactly the count's window (spec divergence **D71**; the current app's today…+1-calendar-month link is the recorded delta).
- **Locale keys:** all count/label strings resolved to existing catalog keys verbatim; **no new keys minted**. The plugin-region error fallback reuses the existing `error.plugin-unavailable` (already in en/fr/ar) — the render integration minted nothing either.
- **Test hooks (C8):** `e2e/TESTIDS.md` defines no dashboard-specific ids; nothing to place.

## Candidate spec refinements

- **Interleaving contributions between built-ins.** The render integration places contributions at each region's tail in merged order; `mergeRegion` can already express a position between two built-ins, and the merge reports one. Realising it needs the built-ins to render from the merged list, which is exactly what the remount analysis argued against — so the spec should say whether tail-placement is sufficient (an anchor then means "which contribution comes first") or true interleaving is required, and if so how a stat's identity stays stable across count updates.
- The internal panel's links can't yet be narrowed to internal-only — needs the inbound list's `kind` contract to grow a selection covering `manual` + `fromInternalOrder` (external is done — see flag above).
- State what a create shortcut should do while its owning vertical is unbuilt (this build applied OMS-REG-DB-01.57's placeholder rule by analogy; since resolved for Order more — the customer-requisition links are the remaining placeholder use).
