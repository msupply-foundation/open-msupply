# Build report — dashboard

**Target stack:** SolidJS + Vite; shared component library `src/ui/` resolved through [`spec/ui-standards/components.md`](../../../spec/ui-standards/components.md).

Regenerated from `spec/dashboard/` (scoped `/spec-build dashboard`). One screen (S1) mounted at both the store root `/` (the landing screen) and the `dashboard` nav destination. Wire surface: the six split count queries in `dashboardCounts.graphql`; the display-gate preferences ride on the shared guard-3 `storeContext` query (no new wire fields — the `PreferencesNode` fields were already present). Gates green: `pnpm check`, `pnpm test` (596 total; 46 dashboard across 5 files), `pnpm build` (DashboardPage = its own lazy chunk, 14.43 kB / **3.85 kB gzip**).

**The dashboard owns the plugin-region semantics** (branch `448-dashboard-plugin-semantics`): how contributions merge with built-ins and how suppression by published id behaves — the published-id tree (`DASHBOARD_IDS`) plus the pure, unit-tested `mergeRegion` in `regions.ts` (deterministic anchor/order/id placement, suppression, missing-anchor diagnostics). AC-D3/D4/D5 are covered at the logic level.

The **render integration** of those semantics (mounting contributions, honouring suppression at render) is deliberately **deferred to the plugins vertical** (greenfield). The page stays explicit composition — built-ins render directly, gated only by their preference gates — rather than pre-placing plugin mount points against an empty contribution set. Rationale: matching open-mSupply's real shape (`client/packages/dashboard/src/hooks.tsx` merges core + plugin into one list _only because plugins exist there_), the merge-and-render wiring belongs with the consumer; pre-placing it now would either scatter render scaffolding at every container (overkill for zero contributions) or drive rendering through a `<For>` over freshly-merged entries, which risks Solid remounting the stats on every count update (kdd/solid-reactivity-pitfalls). So the semantics ship and are tested; the one deliberate place to add the render integration is the plugins vertical.

## Flags

- **C2 (real backend):** no CI tooling exists for the real-backend leg. Every count value is server-computed and wired verbatim; the client-side logic (gates, links, thresholds, panel states, region semantics) is covered at the logic level. The spec's validation notes record live verification of the counts.
- **Plugin-region render integration is deferred to the plugins vertical (AC-D3–D6).** The dashboard owns and tests the semantics (`regions.ts`: published-id tree + `mergeRegion` — deterministic before/after/end placement, `order`/`id` tiebreak, load-order independence, suppression-of-built-ins-only, missing/hidden/suppressed-anchor → end + diagnostic). It does **not** pre-wire the render against an empty contribution set. Two reasons: (1) matching open-mSupply's real shape — `client/packages/dashboard/src/hooks.tsx` merges core + plugin into one list _only because plugins exist there_, so the merge-and-render belongs with the consumer; (2) Solid-specific — a `<For>` over freshly-merged entries would risk remounting the stats on every count update unless carefully memoised (kdd/solid-reactivity-pitfalls), whereas the current explicit-composition page is remount-safe by construction. When the plugins vertical lands it consumes `mergeRegion` and mounts contributions (each in a `PluginRegionOutlet` error boundary — AC-D6) in that one deliberate place; the suppression cascade (widget/panel → nested pieces) then falls out of the page's nesting.
- **Stock-level links (item catalogue):** the six filtered stock-level stats (out-of-stock all / recently-used, at-risk, low-stock, high-stock, overstocked) link into `catalogue/items` filtered to their counts; total items + the panel title stay unfiltered. The dashboard conforms to the items list's **own** URL filter contract (`ItemsListFilter`: the `lens` stock-status enum + `atRisk` + `min/maxMonthsOfStock`) — the list owns its encoding and expands the lens to the wire `ItemFilterInput` itself; `spec/dashboard/contract.md § navigation correspondence` records this vocabulary. Only internal-order and customer-requisition stats remain on unfiltered placeholders (requisitions vertical unbuilt).
- **Internal vs external inbound links (contract › navigation correspondence):** the inbound-shipments list encodes `type` as a permission-scope query variable, not a URL filter, so the internal/external kind is not currently expressible in a stat link — the two panels' window/status links are otherwise correct but open the same (scope-union) list. Needs the inbound list to expose the kind in its URL contract.
- **Order more (AC-X1):** the internal-order create flow is the requisitions vertical's (unbuilt) — the shortcut is permission-gated then degrades to the registered `replenishment/internal-order` placeholder (the AC-N1 rule applied to the create handoff). Revisit when internal orders ship.
- **Cross-section create-flow imports:** the New inbound / New outbound shortcuts lazily import `CreateInboundShipmentModal` and `CustomerSearchModal` from their owning sections (self-contained modals; loaded on first use). If more consumers appear, hoist to `src/domain/`.
- **Codegen drift in other verticals (C7):** running `pnpm codegen` regenerated `customer-returns` and `outbound-shipments` generated files against the newer pinned schema; those regenerations were reverted (out of scope). Those verticals need a regen + filter-map pass on their next build.
- **Expiring-soon link boundary:** per the captured contract the soon link spans today…today+30 while the count excludes lines already expired (≤ today) — a line expiring exactly today appears in the opened list but is counted under _expired_. Candidate spec refinement: start the soon link at today+1.
- **Locale keys:** all count/label strings resolved to existing catalog keys verbatim; **no new keys minted**. The plugin-region error fallback (ui-surface S2 flags it as genuinely new UI with no key to cite) is minted by the plugins vertical when it builds the render integration — not pre-minted here, since nothing renders it yet.
- **Test hooks (C8):** `e2e/TESTIDS.md` defines no dashboard-specific ids; nothing to place.

## Candidate spec refinements

- The plugin-region **render integration** (mounting contributions via `mergeRegion` + `PluginRegionOutlet`, honouring suppression, minting the error-fallback key) lands with the plugins vertical — the dashboard already owns and tests the semantics. Decide there whether contributions interleave between built-ins (full `mergeRegion` order) or the `PluginRegionOutlet`'s current last-child design suffices, and how to drive the render without Solid remounts (memoised merge).
- Decide the inbound list's URL contract for the internal/external kind so the two panels' links can differ (the contract's `type` note assumes a filterable input).
- The expiring-soon link's lower bound (today vs today+1) — see flag above.
- State what a create shortcut should do while its owning vertical is unbuilt (this build applied AC-N1's placeholder rule by analogy).
