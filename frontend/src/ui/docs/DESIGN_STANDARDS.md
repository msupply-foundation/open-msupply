# Design standards alignment

How we move this app's UI toward the organisation's brand design standards, and a living record of what's been reconciled. The process lives at the top (stable); the [Status](#status) table, [Open decisions](#open-decisions-awaiting-carl), and [Ledger](#ledger) grow as we work through the standards section by section.

## The upstream source

The standards live at **https://msupply-foundation.github.io/ui-standards/** — a single static HTML document (not a JS app), organised by component with stable anchors (`#btn-variants`, `#field-sizes`, `#type-scale`, …). It carries concrete, machine-readable values: hex colours, rem/px sizes, states, breakpoints. It is **work in progress and not fully locked in** (Carl, 2026-07-21), so values will move; that is exactly why we sync incrementally rather than copy once.

Sections present upstream: Typography, Tables, Input Fields, Buttons, Search, Modals & Drawers, Navigation, Tabs, Errors & Feedback, Accessibility.

**Read it precisely, not casually.** `WebFetch` runs the page through a small summarising model that rounds and occasionally mis-attributes values — an early fetch reported `#e95c30` as "danger red" when that hex is in fact our brand TMF Orange. So when reconciling a section, pull the **raw** HTML/CSS of that section's anchor and work from the literal values, never from a summary.

## The single source of truth is our tokens

Components never read the standards site; they read tokens. Every concrete value from the standard lands in [`../styles/tokens.css`](../styles/tokens.css) (a token added to the theme contract with a dark override, per the styling principles in [`../CLAUDE.md`](../CLAUDE.md) — no hard-coded colours, no px for spacing/dimensions). The site is an **upstream we sync from**, not something we paste into component CSS. That keeps the WIP drift contained to one file and one ledger, and means a component "matches the design" precisely when its tokens do.

## The reconciliation loop

Run this per standards section (per component), smallest useful unit first:

1. **Fetch raw.** Pull the section's exact values from the upstream anchor (not a summary).
2. **Diff.** Compare against the current component + the tokens it consumes.
3. **Report.** Produce a three-bucket reconciliation report:
   - ✅ **Matches** — already aligned, no action.
   - ⚠️ **Conflicts** — we differ, and the difference is a real decision (brand/UX), not a typo. These are **surfaced for Carl, never silently overwritten.**
   - ➕ **Gaps** — the standard specifies something we have no token/component for yet.
4. **Decide.** Carl rules on each ⚠️ conflict. Record the ruling under [Open decisions](#open-decisions-awaiting-carl) → resolved.
5. **Implement** against tokens; run `pnpm check`.
6. **Verify** by rendering (dev server / screenshot) — static checks can't catch "compiles clean but looks wrong".
7. **Record** the section's outcome in the [Ledger](#ledger) and flip its [Status](#status) row.

## Ledger

### Error dialogs (`#error-dialogs`) — _reconciled 2026-08-13 (issue #840)_

Raw source: the Errors & Feedback section's **Error dialogs** unit (principles, the five-condition demo, the error-types table, buttons, Show details, voice, a11y) — fetched literal. New component: [`../elements/feedback/ErrorDialog.tsx`](../elements/feedback/ErrorDialog.tsx), consumed by the app's global unexpected-error modal; spec updated atomically ([startup › rules › unexpected API errors](../../../spec/startup/rules.md#unexpected-api-errors), D109). Adopted in full: condition-mapped calm copy (no _Oops! Something's gone wrong._, whose `error.something-wrong` catalog value is now "Something went wrong" app-wide), primary = the fix, Close keeps context, raw strings + quotable timestamp reference behind Show details (collapsed for a server error, open for the unmapped fallback, omitted for self-explanatory conditions), during-an-edit modifier (reassurance line, no dashboard), Go-to-dashboard demoted to a tertiary affordance. Demoed per condition at `#/showcase/dialog` (Error dialogs card).

**Deliberate deviations:**

- **Session expired is not this dialog.** The standard's case 1 ("You've been signed out", Cancel + Log in) is covered by the app's existing re-login modal, which embeds the login form itself (spec/startup › re-login) — a richer recovery than a Log-in navigation button; not restyled here.
- **The primary retries by full-page reload**, not by re-firing the failed request — the never-throwing query method reports failures on global state, so the modal holds no request to replay ([kdd/state-management](../../../kdd/state-management/draft-kdd.md)). Close-then-repeat is the request-level retry: the flow behind has released its busy state with values preserved.
- **The edit reassurance line reads "Your changes are still on this screen."**, not the standard's "Your changes are saved on this device." — this app has no offline persistence, so the standard's sentence would be false; ours states the guarantee the spec actually makes (busy state released, values preserved).
- **The dashboard affordance sits beside the buttons** (actions row inline-start, ghost tone), not below them — the dialog's single bottom region; same de-emphasis, no bespoke second row.
- **Enter-to-confirm opted out** (spec/keyboard KB-E2's sanctioned opt-out): the dialog appears unprompted and its primary is a reload, so a stray Enter must not discard the screen.

Follow-on rulings from the same review (Aneesh, 2026-08-13): the reference's **dividers** adopted — a full-bleed hairline above the actions row (`Dialog`'s then-new opt-in `actionsDivider`; off elsewhere) and an inset hairline above Show details, whose summary takes the reference's rotating `›` chevron; and the **house `Dialog` body padding tightened** (`--space-6` 2rem → `--space-4` 1rem, all card dialogs) — the standard's modal chrome runs 1.25–1.5rem, and 1.25rem sits off the `--space` scale, so we take the nearest on-scale step below rather than mint a literal; same empty-margin argument that already moved the workbench sizes to `--space-4`/`--space-5` (#872). Buttons pinned to the **inline-end** via `Dialog`'s then-new `actionsAlign="end"` (house default stayed centred).

**Extended to every modal (Ling + Aneesh, 2026-08-17, #837).** The error modal's chrome was the right frame for all of them, so it stopped being a per-dialog opt-in: both props are deleted, and `Dialog` now always draws a hairline **under the heading** and another **above the actions**, with the buttons at the inline-end. Two consequences worth recording. First, the heading rule is what makes the second one read as a pair rather than as a stray line near the bottom — adopting only the footer divider, as 08-13 did, left the frame lopsided. Second, the actions hairline sits above the ACTIONS, not above the whole bottom region: a `footer` banner (the stocktake estimate, a validation summary) is the content's last word and belongs on the content side of the line. `titleHidden` drops the heading rule with the heading; `chromeless` drops both, since a hairline needs a surface to divide. The matching behavioural half — a **Cancel on every modal a user can back out of** — is [ui-standards › dialogs § chrome](../../../spec/ui-standards/controls.md#dialog-chrome).

### Dense editor cards — field widths, read-only values, picker chrome _(inbound line editor, 2026-08-11)_

Worked out on the inbound-shipment line-edit modal (`src/sections/inbound-shipments/detail/edit-modal/`), but every decision lands in the shared `DataTable` card model or in `Combobox`, so it applies to any dense editor card. Mechanics and the per-column API: [`CARD_TABLE_MODEL.md`](./CARD_TABLE_MODEL.md) § Field widths.

**Adopted from the site — "Field Widths by Context" (`#field-widths`), via the weighted-columns lever in [header-field-width.html](https://msupply-foundation.github.io/ux-testing/header-field-width.html).** A card group can declare a grid template instead of equal auto-fit tracks: a fixed `rem` track per formatted scalar (numeric quantity 7.5, currency 10), and `minmax(<min>rem, <weight>fr)` per free-text/lookup field, so the leftover lands in proportion to expected data length rather than being split evenly over fields that can't use it. Measured effect on the inbound editor: Location's usable text room 106px → 175px, and every field on one row down to a 1366 laptop.

**Adopted 2026-08-20 — the section's range revision (§ _By Content Type_: "every width is a range").** The fixed tracks above become floor–ceiling ranges (quantity `7.5–9`, currency `10–12`, date `10–11.5`), lookups of unpredictable length (Location, Manufacturer, Campaign, Donor, configured reasons) take `12.5–36rem` at weight 2, and free text (note, comment) keeps the `12.5` floor with **no ceiling** at weight 3 — an uncapped field also removes its group's own ceiling, so `CardView` holds every group to the 80rem measure (`--measure-wide`) instead. The site's corollary — never size a field as a fraction of its row — retires the equal-track `narrowLayout` grids above the tablet line (≤1023px): the wrapping weighted row runs there instead, trading cross-row edge alignment for data-true widths. Worked out on the inbound editor; the stocktake editor carries the same widths. Mechanics: [`CARD_TABLE_MODEL.md`](./CARD_TABLE_MODEL.md) § Field widths.

**Deviation — a usually-empty date floors at `11rem`, not the site's `10`.** The site's floor is measured against `DD/MM/YYYY` plus the calendar icon. Our `DateField`'s empty state shows the all-caps `DD MMM YYYY` placeholder — wider than the digits it stands for — which clips at 10, so the stocktake dates (usually the empty ones) floor at 11 with the ceiling riding up to 12.5. A date that usually holds a value keeps the site's range.

**Deviation — a computed value in a dense entry row is DE-BOXED, not greyed.** The site's forms section says "read-only fields are greyed (muted fill, no active border) but keep the same size and position as editable fields… Computed values are read-only." Both treatments were built and compared. `disabled` means "an input you can't use _right now_" — which is exactly what a PO-locked Cost price is in the same row; a Difference or a Line total is arithmetic and is never typed under any state, so the same grey conflates two things the receiver needs to tell apart. It also costs on the scan: in a row you tab through typing numbers, boxes mean "type here". Follows [`kdd/form-layout`](../../../kdd/form-layout/draft-kdd.md) ("read-only-vs-editable reads from the ABSENCE of an input box") and the outbound line editor's Available figure, which already does this among its Issue inputs. ⚠️ **Conflicts with the site — needs Carl's ruling** on which source wins app-wide.

**A discrepancy earns weight, not colour.** A non-zero Difference goes one step to `--weight-medium`; zero and "nothing shipped yet" stay regular. Colour was tried (the mismatch Alert's own severity, mixed 40% into `--text-body` for AA — measured 8.96:1) and **rejected on review**: a severity hue on a single number in a dense row read as an error state rather than as a value worth noticing. Weight is also the accessible channel — nothing rides on hue — and the figure carries an explicit `+` on an over-receipt so direction survives greyscale.

**Picker chrome — clear and chevron each keep a slot.** The reference doc's "clear and chevron share a slot" (swap on hover/focus) was implemented and **reverted**: it puts a destructive control on the pixel a benign one occupied a moment earlier — aim for the chevron, land on ✕, lose the selection with no undo — and it depends on hover, which the tablet form factor doesn't have. Both slots tightened to 1.75rem with no inline padding instead; the ✕ is muted at rest and brightens on hover/`:focus-within`.

**Leading magnifier only where the list is worth typing at.** It renders when the field is EMPTY _and_ the picker has offered ≥10 options (latched on the largest count seen, so a server-backed list narrowing to one row can't blink it off). Its job is to say the list is searchable — the one thing the chevron alone doesn't convey, since a plain `Select` looks identical without it — so on a handful of options it is signage for something nobody needs to do, and once a value is committed the cue is spent while the value needs the width. Consequence, accepted: a server-backed picker shows none until first opened, because `AsyncCombobox` defers its first fetch.

**Card body labels take the dense scale.** Body fields render their caption through `LabelledValue size="small"` (0.8125rem — the site's `.field-label--small`). At the 14px default the caption sat a step _larger_ than a `size="small"` control's 13px text. The card's identity row keeps the full-size label — it reads as the card's heading.

⚠️ **Open: the site's `.field-label` weight has moved again.** It now reads `font-weight: 400`; the 2026-07-22 entry below recorded the spec at **500**, and we deliberately went to **600** on 2026-07-30 (see that entry). So the site and this repo have moved in opposite directions since the last reconciliation. Not actioned — a re-reconciliation call for Carl, not a drift to silently correct.

### Collapsible buttons (`#btn-icons`) — _added 2026-07-22_

Opt-in `collapsible` prop on `<Button>`: at phone widths (**≤767px**, the spec's breakpoint) a labelled button sheds its label to just the icon, to save toolbar space. The label stays in the DOM but **visually hidden** (clip, not `display:none`), so the button keeps its accessible name with **no aria-label** — a cleaner a11y route than the spec's `display:none` + aria-label (no name/label duplication to drift). Tooltip (`title`) skipped at this tier: phone collapse is a no-hover context. **Default is off**, gated by a single module constant `COLLAPSIBLE_BY_DEFAULT` in `Button.tsx` — flip that one line to make collapse the app-wide default later (`collapsible={false}` always opts out). Verified: on a 420px viewport the collapsible buttons render icon-only and keep the accessible name; non-collapsible keep their label; desktop unchanged.

**Second tier, `collapsible="narrow"` — _added 2026-08-14_.** Same collapse, over the whole narrow-viewport range (**≤1023px**, `breakpoints.navOverlay` — the line at which the nav becomes an overlay and dialogs go full screen). For a **page header's action cluster**, which is a vertical-space problem rather than a toolbar-crowding one: four labelled header buttons need ~38rem, more than a tablet has left beside the breadcrumb, so the cluster wrapped onto a row of its own and cost the page a row of table rows. Icon-only they sit on the breadcrumb's line. Two constraints this tier adds over the phone one, both because a tablet **does** hover: pass `title` as well (ui-standards asks an icon-only button to carry a tooltip), and make sure sibling icons in the same cluster are **distinguishable** — the outbound header's "Add from master list" moved from `PlusCircleIcon` to `CatalogueIcon` so it isn't a second unlabelled plus beside "Add item". Opt-in per button, per vertical; first adopted by the outbound-shipment detail header, then the inbound-shipment, internal-order and requisition ones. **`<SplitButton>` takes the same prop** — the tier logic and the app-wide default live in `buttons/collapsible.ts`, imported by both, so the two controls can't drift. Its MAIN half collapses and the caret doesn't (it is already icon-only, and its menu still spells every option out), and it needs no `title`: the hidden label is the tooltip, since the label is the control's own selected option. A split button that collapses must carry an `icon` — collapsed it is nothing else (the inbound header's Add gained `PlusCircleIcon` for exactly that).

### Standard buttons — _added 2026-07-22_

`StandardButtons.tsx` — pre-composed wrappers over `<Button>` for the actions that recur in nearly every dialog and form, so callers stop re-deciding tone + label: `OkButton` (primary, reserved for a dialog whose confirming action genuinely isn't a save, e.g. `ConfirmDialog`'s "are you sure?"), `CancelButton` (secondary), `SaveButton` (primary, `SaveIcon`, collapsible by default — for a page/toolbar Save, not a dialog footer), `DialogSaveButton` (primary, icon-less — the dialog-footer Save, per ui-standards › controls § dialogs, D55) and `SaveAndNextButton` (primary, icon-less). Each fixes only its identity — `variant`, `icon`, and `children` are `Omit`ted from the props, everything else a `Button` takes (`onClick`, `disabled`, `loading`, `size`, `type`, `class`, `aria-*`…) passes straight through. Labels come from the shared intl catalog (`button.ok` / `button.cancel` / `button.save` / `button.save-and-next` — the last one added to all three locales), so they translate and stay consistent app-wide. `SaveButton` defaults `collapsible` on (it earns a toolbar slot) but honours `collapsible={false}`. No barrel — imported by direct path, matching the explicit-composition rule. #### Unit 1 revisit — header font size drops to 13px _(Ling, 2026-08-18)_

The site sets `th` at `0.875rem` — the same size as `td` — and separates the header band by weight (500), the `#FAFAFA` fill and the divider hairline alone. Unit 1 recorded that as a **match**. It no longer is: `.th` now takes a new `--table-header-font-size` token at `0.8125rem` (13px), one notch down, and the legacy display shell [`Table.module.css`](../elements/table/Table.module.css) takes it too. ⚠️ **Conflicts with the site — needs Carl's ruling** on whether the app follows the site here.

The case for deviating is that **the site's table section is an English-only mockup**, and column headers are the one place in the app where translation expansion has nowhere to go — a body cell can ellipsise or wrap freely, but a header is clamped to two lines (`.thText`) and forces a min-content floor on its whole column via `overflow-wrap: break-word`. Measuring all 166 real column headers (every `header: () => t('label.*')` under `src/sections`) in the shipped header font, against the `fr/common.json` strings:

|                                                  | 14px (site) | **13px (ours)** | 12px (tried, rejected) |
| ------------------------------------------------ | ----------- | --------------- | ---------------------- |
| French header width vs English                   | +23.8%      | **+14.9%**      | +6.1%                  |
| French headers clipped past 2 lines, 96px column | 17          | **15**          | 12                     |
| …128px column                                    | 7           | **5**           | 3                      |

12px was built first and **rejected on review as too small** (Ling) — it lands on `--text-xs`, the caption step, which reads as a footnote across a wide table and leaves nothing below it on the scale. 13px is the same notch `--input-font-sm` already takes for small fields, so it is an established step rather than a new one, and it keeps the header clearly above caption size while recovering about a third of the French penalty. Note the gain is real but partial — at a 112px column the same 11 French headers still clip at 13px as at 14px; those want a wider column, not a smaller font.

**A table inside a modal opts back to the site's 14px**, via a `:global(dialog) .th` rule in both stylesheets. A modal table is a small, already-dense surface inside its own frame, where the header band needs no help separating from three or four rows of data, and where the shrink only costs legibility. Scoping on the native `<dialog>` every modal renders into means a vertical gets the right size with no prop to thread through.

Render-verified light on `#/showcase/table`; the 12px and 13px comparisons were measured on the running app, not estimated.

### Workbench dialog width — deliberate deviation from the 900px modal standard _(issue #771, 2026-08-04)_

**The standard's figure.** ui-standards gives a large modal ~900px. `Dialog size="large"` takes that as its working width — `56rem` = 896px — replacing the old full-bleed `100vw - 4rem` that #771 was filed against ("lots of empty space").

**Where it doesn't fit, and why we deviate.** #771 anticipated this in the same sentence that set the figure: _"a centred card at a fixed width (~900px if the tables fit, **wider if the stocktake column set forces it**)"_. All six line editors take it — and far enough past it that no card width fits, so they take the new `size="full"` rather than a bigger number:

| Line editor       | What wants the width               | Size                        |
| ----------------- | ---------------------------------- | --------------------------- |
| Inbound shipment  | 21-column line table               | **`full`** (`100vw - 4rem`) |
| Outbound shipment | 20-column line table               | **`full`**                  |
| Stocktake         | 20-column line table               | **`full`**                  |
| Internal order    | context charts, a 64rem region     | **`full`**                  |
| Requisition       | 3-column figure grid, ~50rem basis | **`full`**                  |
| Prescription      | fits a card — takes `full` anyway  | **`full`**                  |

The internal-order and requisition editors got there without a wide table at all, which is the more useful half of this entry:

- **Internal order** — a **charts region** (target-quantity breakdown + the consumption / stock-evolution pair) capping itself at `64rem` so the pair sits side by side, matching the original app. A 56rem card gives a ~53rem body, so the cap is unreachable and the charts stack.
- **Requisition** — a **figure grid** whose `.column` is `flex: 1 1 16rem`, three columns wide on an extra-fields program requisition: ~50rem of basis before gaps, so in a ~53rem body every column sits pinned at its floor with a labelled figure and its measure word squeezed into 16rem.

Both were first assessed on their most obvious capped region (the requisition's stats block caps at 50rem and fits `large` fine) and both were judged wrong on that basis, then corrected against the running app. The lesson: the question is **what the widest self-capping region inside the modal asks for** — and check every such region, not the first one you find. Column count is a symptom, not the test.

**And one region can't be measured at all.** The internal-order editor hosts a `PluginSlotOutlet` (`infoPanelContributions`, spec/plugins § S1) between the form and the charts. What lands there is a _deployment's_ decision, not ours — the CIV plugin contributes a six-column table (Structure · AMC · Quantity used · Available stock · Adjustments · Period). A host modal cannot size itself for content it will never see, and picking a card width for it means picking one that some deployment's panel will overflow. So: **a line editor that hosts a plugin slot takes `full`**, independent of what its own content measures. The requisition editor has no slot today; if it gains one, this reasoning already covers it.

**The prescription editor takes `full` on consistency alone** (James, 2026-08-04). Its 9-column table genuinely does fit a card — it is the one line editor that was measured and passed. It moves anyway because a user stepping between the six editors should meet one surface shape, not two, and because "line editors are sheets" is a rule that survives a column being added to any of them. Recorded here so the next reader doesn't measure it and "correct" it back.

### ⚠️ Not yet assessed: the other `size="large"` callers

`.large` becoming a 56rem card changed **every** caller, not just the line editors — and the ten below were never looked at. They were full-bleed before this change, exactly as the line editors were, and four of them carry tables in the same width class as the ones that turned out cramped. Assess them against the rule above before assuming they are fine:

| Modal                                               | Columns                             |
| --------------------------------------------------- | ----------------------------------- |
| Supplier returns — ReturnItems / ReturnFromShipment | **15** (shared `returnLineColumns`) |
| Customer returns — ReturnItems / ReturnFromShipment | **14** (shared `returnLineColumns`) |
| `CreateOrderAction`                                 | 7                                   |
| `LinkInternalOrderModal`, `ServiceChargesModal`     | 6                                   |
| `RepackModal`, prescriptions `HistoryModal`         | 5                                   |
| `LinkPurchaseOrderModal`                            | 4                                   |
| `AddFromInternalOrderModal`                         | 3                                   |

The four returns modals are the likely ones: at 14–15 columns they sit between the prescription editor (9, fits) and the shipment editors (20–21, does not).

The reasoning that settles it: **#771's empty space was VERTICAL.** Its screenshot is a nearly-empty modal in a full-viewport box, and the fix for that is the 60–80vh height band plus the small pre-pick card — both of which `full` keeps. Narrowing the _width_ never removed any of that emptiness on these three, because the table was never the empty part; at 896px a 20-column table simply hides columns on a desktop that has the room, trading #771's complaint for a worse one. An intermediate 76rem was tried first and read as a regression against the pre-#771 app (James, 2026-08-04, comparing the inbound editor on this branch against main side by side) — it is narrower than full-bleed by ~230px at 1512, so it loses columns without buying anything back.

Note the columns are only reachable via the card ⇄ table toggle (#886); the three shipment/stocktake editors default to **cards**, where the width buys a wider auto-fit card grid rather than fixing a scroll.

**Mechanism.** `size` gains a third value. `full` is `large` plus a width override — Dialog puts both classes on the element, so the flex column, the height band and the body rules live once, and `.dialog.large.bleed` sets `width: calc(100vw - 4rem)` outright. Below the navOverlay line (1024px) `data-fullscreen` takes over for both, as before. `widthRem` also now sets the working width in `large` (it used to be ignored there), which is the knob for a table that wants a bigger card rather than the full viewport; it stays inert at `full`, where the five editors use it for their pre-pick search card only.

**Open.** This is a width decision, not a column-fit one — 21 columns still won't all fit at 1448px, so a desktop table view still scrolls horizontally. The lasting fix is fewer default columns in the table view, not a wider box.
