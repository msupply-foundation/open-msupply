# Migrating a vertical to the UI library

Companion to [`ADDING_A_COMPONENT.md`](./ADDING_A_COMPONENT.md). That doc is for adding a _new_ component; this one is for bringing an _existing_ vertical (or one screen / tab / modal of it) onto the library — the right components, used correctly, laid out to the standards. The [`migrate-ui` skill](../../../.claude/skills/migrate-ui/SKILL.md) automates the audit-then-fix; this doc is the shared checklist behind it, and the reference for doing it by hand.

## What "correct UI" means

Correct = every UI role is filled by its **registered library component**, composed the way the **reference vertical** (`src/sections/stocktakes/`) and the **showcase** demonstrate — no bespoke look-alikes, no literal colours/sizes, no hand-rolled layout. The bar is conformance requirement **C3** in [`spec/IMPLEMENTING.md`](../../../spec/IMPLEMENTING.md#the-requirements).

## Two references, not one

- **The rules** say what is required — the docs in the table below.
- **The showcase** (`#/showcase`) shows it _working_ — the live, correct composition. Diff the vertical's markup against the matching showcase page. When a screen and its showcase page disagree, the screen is wrong. Pay special attention to the **Header and its toolbar** (`#/showcase/header`) and the **Page / Layout walkthroughs** (`#/showcase/page-layout`) — headers are the most-commonly hand-rolled region.
- **The reference vertical** (`src/sections/stocktakes/`) is those same patterns assembled in real code — copy its shape rather than re-deriving one.

## The reach-for order

For any UI need, reach for the **highest option that fits** — climb down only when the one above genuinely can't do it:

1. **A pre-composed component** — a purpose-built wrapper that already encodes the decision: `StandardButtons` (`SaveButton` / `CancelButton` / `DialogSaveButton` …), `HeaderToolbar`, and other thin layers over primitives. Least to decide, most consistent.
2. **A library component with its defaults** — the mapped component, no prop tuning.
3. **A library component configured with props** — the same component, props for the variation the design needs.
4. **Local page CSS (a CSS module)** — only for genuinely bespoke styling no component or prop covers; scoped to the screen, tokens only (never literals).
5. **Never inline `style`** — an inline style is always a finding. (Inline styles that build layout are also a registry / C3 violation — use `HStack` / `Stack` / `FormRow`.)

This ladder governs both dimension 1 (registry compliance) and dimension 6 (styling): a hand-rolled element that a component higher on the ladder would fill is a finding, and its fix is to climb back up.

## Spec consistency — the durability check

The spec is the source of truth `spec-build` regenerates from, so a migration is only durable if the migrated UI is **what regeneration would produce**. For each screen, run the test: _if this vertical were rebuilt from its spec today, would it come out looking like this?_ Reconcile the implementation with `spec/<vertical>/ui-surface.md` (its content, states, and Layout/region order, and the **roles** it names — each resolved to a component via the [registry](../../../spec/ui-standards/components.md)).

When they disagree, which side is authoritative depends on _what_ disagrees:

- **Pure-UI decisions** (which role/component, layout, composition, styling) — **the current UI standards + registry win.** Update the spec to match: fix the `ui-surface.md` role/content/Layout prose (roles, never component names or CSS — see [`spec/AUTHORING.md`](../../../spec/AUTHORING.md)), or the registry row, and record a deliberate delta in [`DIVERGENCES.md`](../../../spec/DIVERGENCES.md) if it diverges from the reference app.
- **Behaviour, content, or gating** (spec-owned) — **the spec wins.** A UI that does something the spec forbids is a bug to fix in the _implementation_, not a spec edit. Migration changes UI composition only; it never rewrites behaviour to match a drifted screen.

Either way the end state is the same: implementation and spec back in agreement, so the next `spec-build` reproduces the correct UI instead of re-introducing the drift.

## Done-bar

- `pnpm check` green (types, stylelint, theme contract, page-CSS guard, browser floor).
- `pnpm test` green.
- **A human visual pass is required.** Static checks cannot catch "compiles clean but looks wrong". Open each migrated screen and compare it, in light _and_ dark, against the matching showcase page and the stocktakes reference — eyeballing column widths + resizing, field/row spacing, filter chips, empty states, and button tone.
- **The visual pass surfaces library issues too, not only vertical ones.** A vertical inherits the shared `DataTable` / `FilterBar` / `Combobox` / chrome, and using a library component in a context it wasn't built for (a combobox in a filter chip, a lone field in `HeaderToolbar`, a column that won't resize) exposes a **library** gap — not a defect in the vertical's composition. Flag each as a library task (a filed issue for a behaviour bug, an [`ADDING_A_COMPONENT.md`](./ADDING_A_COMPONENT.md) task for a missing variant/editor); the migration does not fix the shared library.

## Boutique / uncovered elements

Some things will not map to a library component — a bespoke table cell, a one-off layout, a special widget. Do not force them into an ill-fitting component, and do not silently leave them hand-rolled. **Flag each one**, tagged as either (a) a candidate for a new library component (→ [`ADDING_A_COMPONENT.md`](./ADDING_A_COMPONENT.md)), (b) a registered ⛔ role in the registry awaiting a build, or (c) a deliberate, documented exception. "Couldn't be covered" must be a recorded decision, never an accident.
