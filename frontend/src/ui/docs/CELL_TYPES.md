# Table cell types & `getCellDefinition`

The catalogue of table **cell types** — the reusable rendering + alignment + default width for each kind of column a vertical shows — and the `getCellDefinition` lookup that turns a common column key into the right one. This is the reference for Phase 3's column-preset work (see [`TABLE_PLAN.md`](./TABLE_PLAN.md)); the cell fragments themselves live in [`tableHelpers.tsx`](../elements/table/tableHelpers.tsx) (plus [`BooleanCell.tsx`](../elements/table/BooleanCell.tsx) / [`ChipListCell.tsx`](../elements/table/ChipListCell.tsx)).

## The model

A **cell fragment** (`CellFragment<T>`) is the slice of a column def a preset owns: `meta` (alignment, wrap) + an optional `cell` render fn (+ grouping `aggregationFn`) + the width props **`size`** / **`maxSize`**. A page spreads it into its own column literal, which still owns identity (`c`), `header`, and `sortKey` explicitly — the preset never touches those, so `keyof T` checking and `K` sort-key inference are unaffected (kdd/type-safety, kdd/explicit-composition):

```ts
{ c: { key: 'expiryDate' }, header: t('label.expiry'), sortKey: 'expiryDate',
  ...getCellDefinition('expiryDate') }
```

Two ways to get a fragment:

- **`getCellDefinition(key)`** — a typed lookup from a **common column key** to its cell type. Many keys map to one type (`name`, `otherPartyName`, `description` all → Text). The key set is a closed union, so an unknown key is a **compile error** — an uncommon column just calls the specific helper instead. Covers only the **argument-free** types.
- **The explicit helper** (`getNumberCell()`, `getExpiryDateCell()`, …) — always available, and the _only_ option for types that need an argument the key can't supply: **Status** (a status→variant map), **Boolean/Flag** (an accessible label), **Linked number** (a nav target). These are never in `getCellDefinition`. (The explicit helpers set only rendering + alignment — **no width**; width lives in `getCellDefinition`, so an explicit-helper column sizes itself with `size`/`maxSize`.)

**Per-call override.** `getCellDefinition(key, meta?)` takes an optional `meta` merged into the preset's meta (caller wins), like the individual helpers — so a per-call `meta` tweak needs no manual merge. To override the width or the cell, spread the result and set the field after it:

```ts
// extra meta merged in (no manual spread of the preset's meta):
{ ...getCellDefinition('numberOfPacks', { cardPosition: 'header-badge' }) }
// override the width (rem → px), or the cell (e.g. an errorable code):
{ ...getCellDefinition('itemName'), size: remToPx(24) }
{ ...getCellDefinition('itemCode'), cell: info => <ErrorableCode …/> }
```

## Width model

Two knobs, both **TanStack's own top-level column props** (px numbers), authored in `rem` and converted with `remToPx`:

- **`size`** — the column's **default** width, delivered as the `min-width` floor (via `getSize()`). A **soft** default: a drag overrides it in _either_ direction, down to TanStack's internal `minSize` (20px). This is what "draggable smaller than the default" relies on.
- **`maxSize`** — a real growth **cap**, delivered as `max-width` (and clamping drag). Used sparingly: only where a hard ceiling makes sense — the fixed-icon **Comment** column and the short **Code** columns. Numbers, dates, currency etc. carry **no** `maxSize` — a good `size` default is enough, and the user should be free to drag them as wide as they like.
- **`minSize`** is **omitted from the `Column` type** on purpose — it's TanStack's drag lower-bound, _not_ the resting min-width (that's `size`), so exposing it is a footgun; passing it is a compile error.

`rem` is used (not `ch`): the width must be a px number for `getSize()` so drag + pinned-column offsets stay coherent, and `ch` can't drive that cleanly. Defaults live per **type** in `KIND_WIDTH` (content-driven); a per-**key** override in the `CELL_DEF` map beats it and is where the **header label width** is accounted for — a number is narrow but its header ("Pack quantity") is not, so several number/currency/date keys carry a wider per-key `size`. Any column also overrides inline via `size`/`maxSize`.

**Not cell types** (structural / display-only, never via a preset): the **selection checkbox** (fixed 3rem/48px hand-rendered leading column) and the **actions** column (`id: 'actions'`, icon buttons, no accessor).

## Delivery status

`size` (→ `min-width`) and `maxSize` (→ `max-width`) are delivered by the renderer today, so a `getCellDefinition` column takes its type/key default width. Still open (the rest of the width pass, [`TABLE_PLAN.md`](./TABLE_PLAN.md) Phase 3): the **flex-sink-can't-shrink** limitation (a resized sink column re-absorbs slack — the fix is to give a _resized_ column explicit `width` semantics), and rolling the presets out to the verticals (currently only the showcases use `getCellDefinition`; the bare helpers carry no width, so vertical tables are unchanged). Tune the default values on render, in one place (`KIND_WIDTH` / `CELL_DEF`).
