i18n · Key Design Decision

Front-end internationalisation architecture

How we add internationalisation to the SolidJS open-msupply-frontend while satisfying most of the functionality of the existing open mSupply React app, without adopting its heavyweight i18next stack.

Context

The existing open mSupply front end (open-msupply/client) ships a full i18next subsystem in packages/common/src/intl: two namespaces (static common + live custom-translations from the server), chained localStorage↔HTTP caching with build-version busting, language detection, ~3,000 keys across 10 languages, RTL, locale-aware number/digit systems, date formatting, English pluralisation, and typed keys.

The new SolidJS app needs most of that behaviour, but the project's technical spec is explicit about minimising bundle size, simplification, and click-through traceability (prefer direct calls over registry/subscriber patterns). A measured production build (see Analysis) shows i18next adds +13.6 KB gzip — ~69% of the entire current app — and provides no SolidJS binding.

A usage census of the reference repo shows string translation is ~99% of all i18n call sites. The remaining formatting/infrastructure surface is real but bounded, and mostly library-independent (built on Intl and date-fns). Out of scope for this decision, by direction: currency (already a manually-linked import), MUI / Material-React-Table widget locales (no MUI/MRT in the new app), and the <Trans> rich-JSX component (0–4 uses).

Options

Option 1 — Port the full i18next stack

Reuse i18next + backends + detector, replacing react-i18next with a thin Solid reactive shim. Maximum reuse of the existing catalogs and identical caching/override behaviour.

Pros:

  • Namespaces, chained cache, version-busting, custom-translations backend, lazy loading and detection all come for free via existing, battle-tested plugins.
  • The ~3,000-key JSON catalogs and their tooling (i18n-unused, translate_locale) port over unchanged.
  • Plural rules for all languages handled by i18next's CLDR support.

Cons:

  • +13.6 KB gzip — ~69% of the current app's total transfer size; the single largest dependency by far.
  • No SolidJS binding — reactivity still needs a hand-written shim, so we don't fully escape custom code.
  • Large configuration surface and a plugin/registry model that runs against the project's simplification and click-through principles.

Option 2 — @solid-primitives/i18n core + hand-rolled gap chosen

Use the Solid-native primitive for the translation core (flatten / translator / resolveTemplate) and hand-roll the bounded gap between it and open mSupply's real needs: plural selection (Intl.PluralRules), namespaces, lazy loading + localStorage cache + version-busting, live custom-translations, detection, and the formatting/metadata layer.

Pros:

  • +~0.5 KB gzip for the ~99% of usage (string lookup + interpolation); the gap layer adds little more.
  • Signal-native reactivity — the translator reads a signal, so locale/dictionary changes re-render with no shim. This is the one place the primitive strictly beats i18next.
  • The gap layer is thinner and more traceable than i18next's config surface, and follows the codebase's existing "signal + explicit async refetch" pattern (e.g. refetchStoreContext).
  • Catalogs are still plain JSON, so existing translations and translation tooling remain reusable.

Cons:

  • We own and test the gap layer (cache, version-busting, custom-translations fetch, detection). Estimated a few hundred lines, but it is our code to maintain.
  • Plural handling for non-English is our responsibility (mitigated: Intl.PluralRules is built in and standard).
  • A maintained but comparatively small community around the primitive (v2, actively published).

Option 3 — Fully hand-rolled (no i18n dependency)

Write the translation core too — a locale signal, flat dictionaries, and a {{token}} resolver — plus the same gap layer, with zero i18n dependencies.

Pros:

  • Absolute smallest bundle (+0.33 KB gzip) and zero third-party i18n surface.
  • Total control and traceability.

Cons:

  • Re-implements what the primitive already does well (reactive lookup, flatten, template resolution, typed chained access) for a saving of only ~0.15 KB over Option 2.
  • More surface to test for no meaningful byte or capability benefit; the primitive is a better-tested version of the exact same code.

Decision

Option 2 — adopt @solid-primitives/i18n and hand-roll the gap layer.

The primitive covers the dominant ~99% of usage for a fraction of a kilobyte and gives us reactivity for free — the two things that most matter. The remaining infrastructure and formatting layer is bounded, largely library-independent, and better owned than pulled in via i18next at ~27× the byte cost and against our simplification principles. Hand-rolling the core as well (Option 3) saves only ~0.15 KB while duplicating solved problems, so we take the maintained primitive as the core and reserve our effort for the gap.

Consequences

  • A new src/intl module owns the translator, namespaces, cache, custom-translations fetch, detection, and formatting — following the codebase's signal + explicit-refetch idiom.
  • Catalogs remain plain per-language JSON; LocaleKey is derived from the English source, keeping t() typed.
  • Custom-translations refresh is wired via a direct call from whatever observes the need (e.g. sync completion / login), not a subscriber registry.
  • Out of scope, tracked separately: currency (manual import), MUI/MRT locales, <Trans>.
  • If the gap layer ever outgrows its weight, the primitive can be swapped for a heavier core behind the same src/intl surface without touching call sites.

Implementation is specified in the Implementation plan.
