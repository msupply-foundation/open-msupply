The existing system

The React app's i18n lives in packages/common/src/intl. It is a full i18next stack — not a thin wrapper — combining i18next, react-i18next, i18next-chained-backend, i18next-localstorage-backend, i18next-http-backend, and i18next-browser-languagedetector. Around that core sits a formatting and metadata layer built on Intl, date-fns, currency.js and pluralize.

The concrete capabilities:

  • Two namespaces — common (≈3,000 keys, shipped as static JSON per language) and custom-translations (fetched live from the Rust server at /custom-translations?lng={{lng}}, so a deployment can override strings without a rebuild).
  • Chained caching — localStorage first (7-day TTL, keyed by a build-time LANG_VERSION for cache-busting), falling back to HTTP; a custom GetBackendByNamespace delegator routes each namespace to its own backend.
  • Language detection — querystring → cookie → localStorage → sessionStorage → a custom browser detector → htmlTag; plus per-user locale persistence.
  • 10 languages — ar, en, es, fr, fr-DJ, ps, prs, pt, ru, tet; with RTL for ar/prs/ps.
  • Locale-aware numbers — Arabic-Indic and extended-Arabic digit systems, wired into i18next's {{x, number}} formatter (with a documented ICU workaround for Pashto).
  • Dates (date-fns per locale: localised date/time, relative time, age), currency (currency.js), English pluralisation (pluralize), server-error translation, and localised full names.
  • Typed keys — LocaleKey derived from en/common.json, giving a typed t(key).

What the primitive gives — and where it stops

@solid-primitives/i18n (2.2.1, ~27 KB unpacked, +0.47 KB gzip in a production build) is a set of small composable primitives, not a framework. Here is the boundary.

Provided by the primitive

  • flatten(dict) — flattens a nested dictionary to dotted keys.
  • translator(() => dict, resolveTemplate) — a reactive lookup with {{token}} interpolation.
  • resolveTemplate — the interpolation resolver.
  • chainedTranslator / scopedTranslator — typed access & module scoping.
  • Reactivity is native: the translator reads a signal, so any dictionary or locale change re-renders.

The gap we must build

  • Plural selection for non-English (CLDR categories via Intl.PluralRules).
  • Namespaces — common + custom-translations, with fallback.
  • Loading & caching — lazy per-language fetch, localStorage cache, LANG_VERSION busting.
  • Live server overrides — fetch /custom-translations, merge, invalidate.
  • Language detection + per-user locale persistence + reactive switch.
  • Formatting & metadata — numbers/digits, dates, RTL, name order, server errors.
  • Typed LocaleKey derived from the source catalog.

The primitive covers the ~99% of usage (string lookup + interpolation) in under half a kilobyte. The gap is real but bounded, and — crucially — most of it is the same code regardless of the translation core. The one place the primitive genuinely beats the alternatives is reactivity: it is signal-native, whereas react-i18next has no SolidJS equivalent.

Why not the full i18next stack?

i18next would hand us namespaces, chained caching, the backend delegator, lazy loading and detection largely for free — but at +13.6 KB gzip, roughly 69% of the entire current app (19.8 KB gzip baseline). It also brings no SolidJS binding, so its reactivity would need a hand-written shim anyway, and it pulls a plugin ecosystem and configuration surface that runs against this project's stated simplification and click-through principles (see specs/technical-spec.md).

The gap layer we would write on top of the primitive is thinner than i18next's config surface, fully traceable, and costs almost nothing in bytes. The trade is that we own and test that layer — which the decision record weighs explicitly.

Conclusion

Adopt @solid-primitives/i18n as the translation core and hand-roll the gap between it and open mSupply's real needs. The heaviest usage is covered by the primitive for ~0.5 KB; the remaining infrastructure and formatting layer is bounded, largely library-independent, and better owned than imported at 27× the byte cost. Currency, MUI/MRT locales and <Trans> are out of scope. → See the Decision record and Implementation plan.
