i18n · Implementation plan

Hand-rolling the gap on @solid-primitives/i18n

A concrete plan for the src/intl module: use the primitive for the reactive translation core, then build the bounded gap — plurals, namespaces, caching, live server overrides, detection, and formatting — following this project's signal + explicit-refetch, click-through conventions.

Module layout

One folder, src/intl, mirroring the shape of src/store / src/api: plain signals for global state, explicit async functions for anything that fetches, and small components that own their markup. No registry, no provider gymnastics.

1 · Translation core

A locale signal and a dictionaries signal feed the primitive's reactive translator. The translator re-runs whenever either signal changes, so every t() call site updates on language switch with no extra wiring. 

// src/intl/intl.ts
import { createSignal, createMemo } from 'solid-js';
import * as i18n from '@solid-primitives/i18n';
import type { LocaleKey, SupportedLocale } from './locales';
import { pluralCategory } from './plural';

// Global state: current locale + the flattened dictionary for it.
// Empty until loadDictionary lands — callers show their existing loading state.
const [locale, setLocale] = createSignal<SupportedLocale>('en');
const [dictionaries, setDictionaries] =
  createSignal<Partial<Record<SupportedLocale, i18n.BaseDict>>>({});

const dict = createMemo(() => dictionaries()[locale()] ?? {});
const translate = i18n.translator(dict, i18n.resolveTemplate);

// Typed t(): key is a LocaleKey; falls back to the key when missing.
export const t = (key: LocaleKey, vars?: Record<string, string | number>) =>
  translate(key as string, vars) ?? (key as string);

// tPlural picks the CLDR category suffix (key_one / key_other / key_many …),
// then defers to t for interpolation ({{count}}).
export const tPlural = (key: LocaleKey, count: number,
  vars?: Record<string, string | number>) => {
  const cat = pluralCategory(locale(), count);              // 'one' | 'other' | …
  const chosen = `${key}_${cat}` as LocaleKey;
  return t(chosen, { count, ...vars });
};

export { locale, setLocale, dictionaries, setDictionaries };

This is the whole "did we keep the primitive?" answer: flatten is applied in loadDictionary, translator + resolveTemplate are the primitive, and reactivity falls out of the signals. Everything below is the gap.

2 · Plural selection

The primitive has no pluralisation. The existing app leans on i18next's CLDR rules; we replace that with the platform Intl.PluralRules — standard, zero-dependency, correct for all our languages. 

// src/intl/plural.ts
const cache = new Map<string, Intl.PluralRules>();

export const pluralCategory = (locale: string, count: number): Intl.LDMLPluralRule => {
  let rules = cache.get(locale);
  if (!rules) { rules = new Intl.PluralRules(locale); cache.set(locale, rules); }
  return rules.select(count);   // 'zero' | 'one' | 'two' | 'few' | 'many' | 'other'
};

Catalog keys follow i18next's suffix convention (attempts_one, attempts_other), so the existing JSON stays compatible. English-only word pluralisation (getPlural, 45 uses) is a separate, simpler helper in intlUtils.ts using pluralize — unchanged from the React app.

3 · Namespaces, loading & caching

Two namespaces: common (static JSON shipped with the build) and custom-translations (fetched live from the server so a deployment can override strings without a rebuild). Custom overrides win on merge. localStorage caches each language, busted by a build-time LANG_VERSION. 

// src/intl/loadDictionary.ts
import * as i18n from '@solid-primitives/i18n';
import { graphqlFetch } from '../api/graphql';           // or fetch() for static JSON
import { readCache, writeCache } from './dictionaryCache';
import { setDictionaries } from './intl';
import type { SupportedLocale } from './locales';

// Explicit async refetch, mirroring refetchStoreContext: callers await it and
// show a loading state until it lands. Failures leave the dictionary empty and
// are surfaced by the global error handling — the caller simply keeps loading.
export const loadDictionary = async (locale: SupportedLocale) => {
  const cached = readCache(locale);                       // checks LANG_VERSION + TTL
  if (cached) { merge(locale, cached); return; }

  // common: static, served with the bundle (lazy per language)
  const common = await import(`./locales/${locale}/common.json`)
    .then(m => m.default).catch(() => ({}));

  // custom-translations: live from server, language-scoped (v2) or flat (v1)
  const custom = await fetchCustomTranslations(locale).catch(() => ({}));

  const flat = i18n.flatten({ ...common, ...custom });    // custom overrides common
  writeCache(locale, flat);
  merge(locale, flat);
};

const merge = (locale: SupportedLocale, flat: i18n.BaseDict) =>
  setDictionaries(prev => ({ ...prev, [locale]: flat }));
// src/intl/dictionaryCache.ts — localStorage with version busting
declare const LANG_VERSION: string;   // injected by webpack DefinePlugin (build timestamp)
const TTL_MS = 7 * 24 * 60 * 60 * 1000;
const keyFor = (locale: string) => `oms_i18n_${locale}`;

export const readCache = (locale: string) => {
  try {
    const raw = localStorage.getItem(keyFor(locale));
    if (!raw) return undefined;
    const { v, at, flat } = JSON.parse(raw);
    if (v !== LANG_VERSION || Date.now() - at > TTL_MS) return undefined;
    return flat;
  } catch { return undefined; }
};
export const writeCache = (locale: string, flat: unknown) =>
  localStorage.setItem(keyFor(locale),
    JSON.stringify({ v: LANG_VERSION, at: Date.now(), flat }));

Build change: add webpack.DefinePlugin({ LANG_VERSION: JSON.stringify(String(Date.now())) }) and copy src/intl/locales into the output (or rely on the dynamic import() above, which lets webpack code-split each language — the leaner choice given the lazy-loading spec). The custom-translations endpoint URL comes from src/config.ts, alongside GRAPHQL_URL.

4 · Detection, persistence & switching

Resolve an initial locale, persist the user's choice, and switch reactively. Language is normally set from the user profile on login; detection is the fallback for first paint and refresh. 

// src/intl/changeLanguage.ts
import { setLocale, locale } from './intl';
import { loadDictionary } from './loadDictionary';
import { isSupported, type SupportedLocale } from './locales';
import { persistUserLocale } from './detectLocale';

// Direct call — click-through traceable. Awaited by the caller (e.g. the
// language switcher, or login once the profile locale is known).
export const changeLanguage = async (code: string, username?: string) => {
  if (!isSupported(code)) return;
  await loadDictionary(code as SupportedLocale);   // ensure strings before flip
  setLocale(code as SupportedLocale);
  if (username) persistUserLocale(username, code as SupportedLocale);
};

Detection order (querystring → localStorage → navigator.languages → 'en') lives in detectLocale.ts as a short pure function — a much smaller surface than i18next-browser-languagedetector's plugin chain, covering the cases the app actually relies on. Per-user locale is stored via the same localStorage idiom as src/appData.ts.

5 · Formatting & metadata (library-independent)

This layer is identical whichever translation core is chosen — it is built on Intl and date-fns, not on the primitive. Ported largely as-is from the React app, minus currency.

formatNumber.ts

  • Intl.NumberFormat with digit-system overrides: ar→Arabic-Indic, prs/ps→fa-AF extended-Arabic (carry over the documented Pashto ICU workaround verbatim).
  • format, round, roundUpToWholeNumber, parse (separator/decimal aware, converts Indo-Arabic numerals back).

formatDateTime.ts

  • Per-locale date-fns objects, imported individually (they don't tree-shake) — en, fr, ar, es, ru, pt, fa (for prs/ps).
  • localisedDate/Time/DateTime, relativeDateTime, localisedDistanceToNow, getDisplayAge — the methods behind the 61 call sites.

intlUtils.ts collects the small metadata helpers: isRtl (ar/prs/ps), currentLanguageName, languageOptions, getLocalisedFullName, getPlural (English, via pluralize), translateServerError (key lookup with a camelCase fallback), and invalidateCustomTranslations (clear the cache entry + re-run loadDictionary for the custom namespace).

6 · Integration points

  • Startup (App.tsx): before first paint, resolve the locale via detectLocale and await loadDictionary(locale) inside the existing runStartup loading phase — so the app never flashes untranslated keys.
  • Login: once the user profile's language is known, call changeLanguage(profileLocale, username) — a direct call, no event.
  • Sync completion: whatever observes a completed sync calls invalidateCustomTranslations() directly (same pattern the spec prescribes for checkAuth() / refetchStoreContext()), picking up server-side string changes.
  • RTL: set document.dir from isRtl(locale()) in a top-level createEffect, so direction follows the locale signal.
  • Call sites: replace inline strings with t('login.title') etc.; the LoginPage is the first consumer (it already has the strings the earlier benchmark used).

7 · Type safety

Keep t() typed by deriving LocaleKey from the English source catalog, with the same plural-suffix normalisation the React app uses (so attempts_one also permits attempts): 

// src/intl/locales.ts
import type common from './locales/en/common.json';   // type-only: not bundled

type PluralSuffix = 'zero'|'one'|'two'|'few'|'many'|'other';
type Normalize<K> = K extends `${infer B}_${PluralSuffix}` ? B | K : K;
export type LocaleKey = Normalize<keyof typeof common>;

Consistent with the technical spec's type safety section: no remapping of catalog data, and the one as string in intl.ts is confined to the trusted core where the key set is known correct — exactly the kind of trusted-layer cast the spec permits.

Testing

  • Unit (vitest): pluralCategory per language; formatNumber digit systems and parse round-trips; date helpers per locale; cache version-busting and TTL; custom-over-common merge precedence; LocaleKey normalisation (type-level).
  • Behavioural: switching language re-renders t() consumers (signal reactivity); document.dir tracks RTL locales; invalidateCustomTranslations forces a refetch.
  • Parity check: for a sampled set of keys and each locale, assert our output equals the React app's for numbers, dates, and plurals — the migration's safety net.

Out of scope (explicit)

  • Currency — already a manually-linked import; not re-implemented here.
  • MUI / Material-React-Table locales — the new app has no MUI/MRT dependency.
  • <Trans> / rich JSX interpolation — 0–4 uses; if ever needed, a small component can compose t() output, but it is not part of this plan.
  • Automatic translation & unused-key tooling (translate_locale, i18n-unused) — can be ported later; not required for functionality.

Net result

A typed, reactive, lazily-loaded i18n with server-side overrides and locale-aware formatting — matching the functionality the app actually uses — built on a ~0.5 KB primitive plus a few hundred lines of traceable, library-independent gap code, instead of a 13.6 KB framework.
