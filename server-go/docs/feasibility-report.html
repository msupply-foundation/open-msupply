Engineering Feasibility Spike

Porting the Open mSupply backend from Rust to Go

A time-boxed, evidence-driven evaluation. We built a working Go vertical slice against the real schema, GraphQL API, and production databases, then measured it head-to-head with the Rust server. This is what we proved, what it costs, and what still needs answering.

Audience Dev leadership & engineering Status Spike complete; full port not started Date 2026-06-10

Executive summary

The motivation for this evaluation is developer velocity: Rust's compile times, test loop, and on-disk build footprint are a daily tax — and that tax is multiplied when an AI agent is driving development, because an agent runs far more build/test cycles than a human. The spike confirms the velocity gap is large and real, and that the API + database port is mechanically feasible. The dominant unknown — the sync engine — has not been touched, and is the one thing that should gate any go/no-go.

⚠ Big caveat — this is not a like-for-like comparison yet

* The Go figures come from a small vertical slice: roughly 2,700 lines of hand-written Go (plus a 197,000-line auto-generated GraphQL layer and dependencies) measured against ~337,000 lines of real implementation in the Rust server. We are comparing a fraction of the system to the whole. As the Go port grows toward full implementation, its absolute build and test times will grow with it — these numbers are a starting point, not the endpoint.

What the data does and doesn't support:

  • The cold-build gap will narrow as LOC grows. Today's ~90× is inflated by the slice being small; expect it to shrink toward ~10–20× at full size (projection below).
  • The per-edit and test-loop advantage is largely structural and size-independent. Go's incremental compile is package-scoped and cached (only the changed package + its dependents rebuild), and gqlgen's codegen is paid once ahead-of-time, whereas Rust's async-graphql macros re-expand on every compile. This is the loop that dominates AI-agent iteration, and it should stay fast even at full size.

Why this matters for AI-driven development

An AI agent's throughput is gated by its feedback loop. Every "edit → build → test" cycle in Rust costs tens of seconds to minutes; in Go it is sub-second to a few seconds. Across the hundreds of cycles an agent runs per task that compounds into a 10–100× difference in iteration throughput — and directly into agent cost and wall-clock. The disk pressure is just as real: during this spike, Rust/CGO builds repeatedly exhausted the disk ("no space left on device"); the pure-Go work never did.

Runtime is a wash where it counts. Rust's web stack is ~2× faster at trivial requests, but on a realistic large query both servers are bottlenecked by Postgres, not the language (Go was even marginally ahead). For Open mSupply's workload, language runtime speed is not the deciding factor.

The approach

Rather than estimate from theory, we built a real Go vertical slice and compared it to the live Rust server. The slice deliberately exercised the parts most likely to break a port:

  • Exact API contract. Exported the real GraphQL SDL (9,893 lines) from the Rust server and generated the Go server from it — so the API is identical by construction.
  • Real database, both engines. Drove SQLite and a real Postgres 16, including reading live production-shaped databases created by the Rust server.
  • The hard patterns. The linked-table (core/view) model, dynamic filter/sort, N+1 batching (DataLoader), and the version-based migration framework.
  • The "needs Rust?" question. Whether the embedded JavaScript engine (reports + plugins) forces us to keep Rust via CGO.
  • Measurement. Compile time, test time, disk, and a head-to-head load test on the same Postgres database.

Recommended Go stack validated: gqlgen (schema-first GraphQL), database/sql + sqlc + squirrel, jackc/pgx (Postgres), modernc.org/sqlite (pure-Go SQLite), dop251/goja (pure-Go JS).

Build & deploy — cross-compilation and CI

A concrete operational win, separate from raw speed. A pure-Go build cross-compiles to every target from a single machine, with one command and zero extra toolchain — proven for all five targets in the spike. For example, a Windows binary built on a Mac:

# on a developer Mac or any CI runner — produces a Windows .exe, no Windows machine involved CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build -o oms-server.exe ./cmd/server

Today, shipping a Windows build relies on a dedicated Windows build server (plus self-hosted macOS agents for the Mac/Android builds), because cross-compiling Rust — especially with its bundled C SQLite (a CGO dependency) — needs a per-target C toolchain and linker. In the spike, getting even one Rust+CGO target to cross-compile required installing zig, adding a Rust target, and wiring a per-target linker by hand. With a pure-Go server, that dedicated Windows/desktop build server is very likely unnecessary — Windows, Linux (amd64/arm64) and macOS binaries can all come off one CI runner. That is a real reduction in build infrastructure and CI complexity.

Conditions & limits: this holds only while the port stays CGO-free — which the spike showed is achievable, including the JavaScript engine (goja) and a pure-Go SQLite/Postgres stack. Keeping any Rust via CGO reintroduces the per-target toolchain and brings the build-server requirement back. Mobile (Android/iOS) is more than a server binary: the core still compiles pure-Go, but the app / JNI packaging is separate work.

Results 3 — Runtime performance (Postgres head-to-head)

Both servers ran against the same Postgres database and received the byte-identical GraphQL document: a single page (first: 50) of invoices, sorted, including the otherParty DataLoader field — so each server's loader is exercised, not just scalar columns. 50 concurrent users.

⚠ All load testing ran with authentication & authorization disabled

On both servers (Rust via a temporary dev-gate patch + debug_no_access_control; the Go slice has no auth layer yet). Auth and permission-checking overhead is excluded from every number here — it would add cost to both sides, and on the Go side it is itself unported work.

Small query (22 invoices + loader)1,373 · 32 ms1,015 · 46 msServer; Rust ahead

Rust holds a genuine ~2× edge on raw overhead, and stays ahead on the small real query once the DataLoader is in play (1,373 vs 1,015 req/s). On the large query both collapse to ~20–30 req/s — a single count over a million-row joined view (~135 ms) saturates Postgres long before the language matters. At scale the database is the wall, not the server language.

Did the same data come back? Small store: byte-identical (5,925 bytes, loader-resolved names included). The large store initially differed by one row — Rust's invoices query applies a default is_cancellation = false filter (that store has one cancelled invoice) that the slice hadn't replicated. We added that filter to the Go slice; both now return exactly 1,004,135 — and re-running the load test did not change the gap (Go still ~30 vs Rust ~21 req/s). So the throughput difference is not that filter: it's implementation detail (the Go slice selects only the requested columns while Rust loads the full invoice row, plus HTTPS vs HTTP), and at this scale it is Postgres-bound regardless. Pinning the exact residual cause would need query-plan profiling of each server's emitted SQL.

Remaining fairness notes: the servers still don't send byte-identical SQL (the Go slice selects only the requested columns; Rust loads the full invoice row), and Rust served HTTPS vs Go HTTP (negligible here — connections reused). Read the large-query result as "same order, Postgres-bound," not a precise language win.

The honest trade-off — Go's weaker compile-time guarantees

The velocity gains are real, but they come with a cost that matters for a data-integrity-critical system. Rust's type system catches a whole class of "I added something and forgot to handle it everywhere" bugs at compile time; Go largely cannot.

A live example from this spike: adding the is_cancellation filter. In Rust, the surrounding idioms — exhaustive match on the sort/enum types and full destructuring of the filter struct — mean a newly added field or variant won't compile until every site handles it (and unused fields are flagged under deny(warnings)). In Go, adding IsCancellation to the filter struct and forgetting to translate it to SQL compiles cleanly and silently does nothing — the bug surfaces only in a test or in production. Go does not warn on unused struct fields, and its switch has no exhaustiveness check. (We caught exactly this class of gap here via a data-parity diff, not the compiler.)

Mitigations in Go — none equivalent to the compiler: the exhaustive linter (CI-time, catches non-exhaustive switches over typed enums), disciplined tests, or code-generating the filter→SQL mapping from one source of truth so a field cannot be forgotten. These move the guarantee from "compiler" to "CI + discipline."

The same trade-off shows up in column selection. In the load test the Go slice fetched only a fixed subset of columns while Rust's resolver loaded the full invoice row. Fetching only what you need is good practice and lighter on the database — though most impactful for wide rows / large result sets; for a 50-row page it is marginal, and it's available to either server, so it's an implementation choice rather than a language advantage. The catch is how the Go slice does it: the SELECT list and the row-Scan that reads it are hand-written and positional — not type-safe. If the two drift out of sync it's a runtime error or silently wrong data, not a compile error. Rust/Diesel maps rows to typed structs and checks column selections at compile time. The Go answer is sqlc, which generates typed structs from your SQL so a fixed query is compile-checked — recovering the safety for static queries (a dynamic, per-request projection is hard to make type-safe in either language).

This is the core Rust↔Go trade: Rust buys compile-time correctness at the cost of compile speed; Go buys iteration speed at the cost of weaker static guarantees. For Open mSupply — fleet-wide data integrity and sync correctness — this is a genuine factor to weigh, and it raises the importance of test coverage and codegen (e.g. sqlc) in any Go port.

Recommendation & next step

Before any go/no-go: a sync-engine spike (seeking go-ahead)

Everything we've measured points the same way — the developer-velocity case for Go is strong, and the API + database + JS layers are feasible with no Rust dependency. But the sync engine is the decisive unknown, and we have zero evidence on it. We recommend a focused, time-boxed sync-engine spike next: port one or two entity translations plus the push/pull state machine against a real central server, to find out whether sync is "mechanical like the rest" or a genuine multi-month hazard. We are seeking the go-ahead to run it.

Also worth putting on the table (cheaper than a rewrite): much of the compile-time pain can be attacked without porting — a faster linker (lld/mold), sccache, a cranelift dev backend, and crate splitting. If velocity is the goal, this is the low-cost interim while the sync question is answered. (Not yet baselined — we compared against the current, un-tuned Rust build.)

Net read: nothing in the spike argues against the port; the velocity economics strongly favour Go and runtime is Postgres-bound at scale. The remaining risk is concentrated almost entirely in the sync engine — de-risk that before committing.
