Craig Was Right: Postgres Counts Are Slow

…and they're the entire reason large invoice lists collapse under load. The good news: we measured three fixes, the cheapest is ~200 lines of backend code, and it takes a 1M-invoice store from 21 requests/sec to ~1,500–1,900 requests/sec.

Database demoivory_lt (production-shaped copy, 1,004,135 invoices in one store) Load k6, 50 concurrent users, 20 s runs Server Rust release build, local Postgres 16

Executive summary

While load-testing the Rust server against the Go-port spike, both servers collapsed from >1,000 req/s to ~20–30 req/s on a 1M-invoice store — even though every request only asks for 50 rows. The language was irrelevant: 94% of each request is the exact COUNT(*) that feeds the page-list's totalCount, and it runs on every request. Indexes cannot fix an exact count over a million rows. We implemented and benchmarked three strategies — a query-planner estimate, a backend count cache, and client-side count caching — all individually restore ~70–90× throughput, they compose, and a small server-side "clamp" removes the one dangerous failure mode of estimation.

How we got here

This came out of the Rust → Go backend-port spike. To compare the servers fairly we ran identical GraphQL invoice-list queries against the same Postgres database at three scales. On small stores both servers comfortably exceed 1,000 req/s. On the 1M-invoice store, both collapsed to ~20–30 req/s — and the ordering even flipped (Go slightly ahead, partly a connection-pool artefact: Rust caps its pool at 10 connections, the Go spike's was unbounded).

That convergence was the tell. When two completely different implementations hit the same wall, the wall is the database. And the more important realisation: this isn't a Rust-vs-Go question at all — it's a scaling question we already own in production today. Any site whose invoice table grows large will see its list screens degrade exactly this way, on either backend.

What indexing can fix — and what it can't

First suspicion was a missing index, and indexing did matter — just not for the count:

  • Added a composite index (store_id, invoice_number): the sorted 50-row page query now reads exactly 50 rows. Execution time 2.1 ms → 0.9 ms.
  • Dropped the existing single-column invoice_number index — it was actively harmful here: the planner walked the whole-table index in sort order and post-filtered, discarding 707 rows for every 50 returned.
  • But the k6 numbers didn't move (~20 req/s before and after). The count dominates so completely that fixing the page query is invisible until the count is dealt with.
  • We also tried partial and covering indexes for the count itself. Postgres declined them all — correctly. An exact count must visit every matching row; with 1M matches the planner's parallel seq scan (~75–110 ms) is already the cheapest plan there is.

The results

How the exact ↔ estimate switch works (Option A)

It is not "always an estimate". Every count request first runs EXPLAIN (FORMAT JSON) on the already-built, filtered query — same SQL, same bind parameters, just prefixed. EXPLAIN only plans: it reads table statistics and computes selectivity, never touching the rows, which is why it costs ~8 ms at any scale. The planner's row estimate then decides:

  • Estimate ≥ 10,000 → return the estimate. Counting precisely past tens of thousands of rows is expensive, and no user distinguishes 1,004,007 from 1,004,135 in a pager.
  • Estimate < 10,000 → run the real COUNT(*). Small counts are milliseconds-cheap, so most stores keep today's exact behaviour — and this branch self-corrects a wrong-low estimate (stale stats saying "800" when there are 2M rows results in one slow-but-correct count, never a wildly wrong number).
  • EXPLAIN fails for any reason → silently fall back to the exact count.

The failure mode that matters — and the clamp that closes it

Wrong-low estimates would hide data

The frontend derives its page count from totalCount and disables paging past it. If the estimate ran low (worst case ~10% after a bulk import, before auto-ANALYZE), the last pages of the list — the newest invoices under the default sort — would be unreachable. Estimating too high is benign by comparison (one short/empty page at the end).

The fix costs nothing: the resolver already fetched the page, and the page is ground truth. Before returning, the count is clamped against what the page proved:

  • A full page at an offset the count doesn't cover proves at least one more row exists → report offset + rows + 1, so the "next page" button stays alive and the count refines as the user browses. The true end of the list is always reachable.
  • A non-empty short page means the query ran past the end of the data → offset + rows is the exact total; the count snaps to it (this also corrects wrong-high estimates the moment the real last page is reached).
  • Exact counts are never altered by the clamp — every branch is a no-op for them.

Verified live against the 1M store: at offset 1,004,000 (a full page past the 1,004,007 estimate) the API reports 1,004,051 and keeps paging; at offset 1,004,100 (a 35-row short page) it snaps to the exact 1,004,135. Belt-and-braces operational extra: schedule an ANALYZE invoice after bulk loads/sync catch-ups to bound the cosmetic error window.

So SQLite is not off the hook — a 100k-prescription remote pays a measurable count tax on every list request today, it just hasn't reached the cliff the central servers are at. Two SQLite-friendly levers cover it:

  • Most of SQLite's count cost is the join, not the counting. Measured at 100k rows: 25 ms through the production view + name join vs 1.8 ms counting the invoice table directly (13×). The count only needs that join when the filter touches the customer name, so a "skip the join when unused" optimisation — not yet implemented — recovers most of the cost on both databases.
  • Options B and C work fully on SQLite — the count cache turns repeat counts into map lookups, and client-side caching stops paging from re-counting at all.

Frontend changes — what's required vs optional

  • Options A and C need no frontend changes at all. totalCount keeps its shape; the UI is unmodified. (With A, very large totals are estimates displayed as exact numbers — with the clamp, never in a way that hides data.)
  • Option B is the frontend's half of the story: fetch totalCount as a separate query cached per filter (react-query makes this natural), and drop it from the rows query. Because a count depends only on the filter — never on sort or page — paging and re-sorting never re-count. It composes with A or C (measured: 1,790 req/s combined) and additionally benefits SQLite sites. Recommended as a follow-up, one list view at a time.

Recommendation

  1. Ship Option A (planner estimate + clamp) for Postgres, feature-flagged, with the SQLite exact fallback. Smallest change, no frontend work, ~70× measured.
  2. Ship the index migration: add composite (store_id, invoice_number); drop the harmful single-column invoice_number index (after checking no other query depends on it).
  3. Keep the count-skip (don't count when totalCount isn't selected) — free, and it's what makes Option B possible later.
  4. Add the skip-the-join count (count the invoice table directly unless the filter uses the customer name): 13× cheaper exact counts, benefits SQLite remotes — including the 100k+ prescription sites — and Postgres alike. Small, not yet implemented.
  5. Evaluate Option C against real sync traffic before trusting it: the cache clears on every invoice write, and a busy central server syncs invoices continuously — the hit rate is the open question. (It's also per-process: multi-instance deployments would need shared invalidation.)
  6. Adopt Option B in the frontend as a follow-up — exact counts, works everywhere, and removes the count from every page click permanently.

Caveats on the numbers

Single local Postgres 16 on developer hardware; one filter shape (store + non-cancelled); warm cache; auth bypassed (develop-mode build, same as the spike baseline — the baseline re-measured identically at 21 req/s, so comparisons are apples-to-apples). The earlier Rust-vs-Go throughput comparison carries a connection-pool asymmetry (Rust pool = 10, Go unbounded); the strategy benchmarks above are unaffected (single server, pool constant). All schema/index changes were made to the disposable test copy only.
